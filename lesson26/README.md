# 第26章 運用管理（SNMP・ログ・障害切り分け）

作ったネットワークを安定して動かし続けるための章です。SNMPによる監視、syslogとNTP、そして障害時の切り分け手順は、午前Ⅱでも午後でも定番のテーマです。

## 1. SNMP（MIB・ポーリングとトラップ・v2cとv3）

ネットワーク機器の状態を集中監視するための標準プロトコルが **SNMP**（Simple Network Management Protocol）です。

### 登場人物

| 役割 | 動作 |
|---|---|
| **SNMPマネージャ** | 監視サーバ。各機器に問い合わせ、情報を集める |
| **SNMPエージェント** | 監視される機器側のソフトウェア。問い合わせに答える |
| **MIB** | 管理対象の情報（CPU使用率、ポート状態など）を**ツリー構造**で定義したデータベース |

### ポーリングとトラップ

- **ポーリング**: マネージャが**定期的に**エージェントへ問い合わせて値を取得します（GET要求）。定期取得なので、障害発生から検知まで最大でポーリング間隔分の遅れが出ます
- **トラップ**: 障害などのイベント発生時に、**エージェントが自発的に**マネージャへ通知します。即時性が高い一方、UDPで送られるため届かない可能性もあります

実務では両方を組み合わせ、即時検知はトラップ、状態の定期確認と傾向把握はポーリングで行います。

### v2cとv3

**SNMPv2c**は「コミュニティ名」という合言葉で認証しますが、**平文で流れる**ため盗聴に弱い方式です。**SNMPv3**は**利用者ごとの認証と通信の暗号化**をサポートし、セキュリティ要件が高い環境で使われます。

> 💡 コツ: 🔴 「ポーリング＝マネージャから定期取得」「トラップ＝エージェントから自発通知」。主語の向きで覚えるのが鉄則です。

### 確認問題

**問1.** SNMPトラップの説明として、適切なものはどれか。

1. マネージャが定期的にエージェントへ問い合わせて値を取得する動作
2. マネージャがエージェントの設定値を書き換える動作
3. イベント発生時に、エージェントが自発的にマネージャへ通知する動作
4. エージェント同士が互いの死活を監視し合う動作

<details><summary>答えと解説</summary>

正解: **3**

トラップは、障害などのイベントを契機にエージェント側からマネージャへ自発的に送られる通知で、即時性に優れます。1番目はポーリング（GET）、2番目はSET操作の説明です。SNMPはマネージャとエージェントの間の仕組みであり、エージェント同士が監視し合うプロトコルではありません。

</details>

**問2.** MIBの説明として、適切なものはどれか。

1. 機器の管理情報をツリー構造で定義したデータベース
2. SNMPの通信を暗号化するための鍵の集合
3. マネージャの画面に表示するグラフのテンプレート
4. エージェントのIPアドレスの一覧表

<details><summary>答えと解説</summary>

正解: **1**

MIB（Management Information Base）は、CPU使用率やインタフェースの状態といった管理対象情報をツリー構造で体系的に定義したデータベースで、マネージャとエージェントはこの定義を共有して情報をやり取りします。暗号鍵の集合やグラフのテンプレート、単なるアドレス一覧ではありません。

</details>

**問3.** SNMPv2cと比較したSNMPv3の特徴として、適切なものはどれか。

1. コミュニティ名を平文で送ることで互換性を高めている
2. トラップ機能が廃止され、ポーリング専用になっている
3. 監視対象がルータだけに限定されている
4. 利用者ごとの認証と通信の暗号化をサポートしている

<details><summary>答えと解説</summary>

正解: **4**

SNMPv3はユーザベースの認証と通信の暗号化をサポートし、v2cの弱点を解消したバージョンです。コミュニティ名を平文で送るのはv2c側の特徴（弱点）です。v3でも通知の仕組みはあり、監視対象が特定の機器種別に限定されることもありません。

</details>

**問4.** ポーリング間隔5分のSNMP監視を行っているが、障害の検知が最大5分遅れることが課題になっている。即時に近い検知を実現するために行うべきことはどれか。

1. MIBのツリー構造を浅くする
2. 機器からマネージャへのSNMPトラップ送信を設定する
3. ポーリングを停止して手動確認に切り替える
4. コミュニティ名をより長い文字列に変更する

<details><summary>答えと解説</summary>

正解: **2**

ポーリングは定期取得のため検知が間隔分遅れます。イベント発生時にエージェント側から即時通知されるトラップを併用するのが定石です。MIBの構造やコミュニティ名の長さは検知の速さと関係がなく、ポーリングを止めて手動確認にすれば検知はむしろ遅く不確実になります。

</details>

## 2. ログと時刻（syslogとNTPの階層）

障害解析やセキュリティ調査の土台になるのが**ログ**と**正確な時刻**です。

### syslog

**syslog**は、機器やサーバのログメッセージを**ログサーバへ転送して集約する**標準的な仕組みです。メッセージには、どの機能が出したかを示す**ファシリティ**と、重大度を示す**セベリティ**が付きます。伝統的に**UDP（ポート514）**で送られるため、ネットワーク障害時にはメッセージが欠落する可能性があります。

ログを1か所に集約しておくと、機器自体が故障・侵害されてもログが残り、複数機器を横断した解析ができます。

### NTPと時刻同期

複数機器のログを突き合わせて「何が先に起きたか」を追うには、**全機器の時刻がそろっている**ことが大前提です。時刻合わせのプロトコルが**NTP**（Network Time Protocol）です。

NTPは**Stratum（ストレータム）**という階層構造をとります。

| 階層 | 意味 |
|---|---|
| Stratum 0 | 原子時計やGPSなどの一次基準時計そのもの |
| Stratum 1 | 一次基準時計に直結したNTPサーバ |
| Stratum 2以降 | 上位のNTPサーバから同期（1階層下がるごとに+1） |

数値が**小さいほど基準に近い**上位のサーバです。

> 💡 コツ: 🔴 午後試験の運用設計では「ログ集約＋NTPによる時刻同期」がセットで問われます。「時刻がずれていると複数機器のログを突き合わせられない」という理由まで書けるようにしましょう。

### 確認問題

**問1.** 複数のネットワーク機器のログを突き合わせて障害発生の順序を解析するために、前提として必要なものはどれか。

1. 全機器のホスト名を同じにしておくこと
2. NTPで全機器の時刻を同期しておくこと
3. 全機器のログを暗号化しておくこと
4. ログの出力形式をすべてバイナリにしておくこと

<details><summary>答えと解説</summary>

正解: **2**

機器ごとに時刻がずれていると、ログのタイムスタンプを比べても事象の前後関係が分からなくなります。NTPによる時刻同期は横断的なログ解析の大前提です。ホスト名はむしろ機器を区別するために別々であるべきで、暗号化や出力形式は保全や管理の論点であり、順序解析の前提ではありません。

</details>

**問2.** syslogによるログ転送の特徴として、適切なものはどれか。

1. セベリティと呼ばれる重大度の区分がメッセージに付与される
2. ログは必ず暗号化されて転送される
3. 転送には常にTCPが使われ、欠落は発生しない
4. ログサーバから各機器へログを配布する仕組みである

<details><summary>答えと解説</summary>

正解: **1**

syslogメッセージには重大度を示すセベリティと、出力元機能を示すファシリティが付与されます。伝統的なsyslogはUDP（ポート514）で送られるため欠落の可能性があり、暗号化も標準では行われません。また、各機器からログサーバへ送って集約する仕組みであり、配布の方向が逆です。

</details>

**問3.** NTPのStratumに関する記述として、適切なものはどれか。

1. Stratumは通信の暗号強度を表す指標である
2. Stratumの値が大きいほど正確な上位のサーバである
3. Stratum 1は一般の社内PCに割り当てられる階層である
4. Stratum 1は一次基準時計に直結したサーバであり、値が小さいほど基準に近い

<details><summary>答えと解説</summary>

正解: **4**

Stratumは基準時計からの階層を表し、原子時計やGPSなどの一次基準時計がStratum 0、それに直結したNTPサーバがStratum 1で、1階層下がるごとに値が1増えます。つまり値が小さいほど基準に近い上位です。暗号強度の指標ではなく、社内PCは通常もっと下位の階層から同期します。

</details>

**問4.** 各機器のローカルディスクだけでなく、ログサーバにもログを集約して保管する利点として、最も適切なものはどれか。

1. 各機器のディスク容量を増設できる
2. ログの発生件数そのものを減らせる
3. 機器の故障や不正侵入でローカルのログが失われても、サーバ側に記録が残る
4. 時刻同期が不要になる

<details><summary>答えと解説</summary>

正解: **3**

ログを外部に集約しておけば、機器の故障時はもちろん、侵入者がローカルのログを消して痕跡を隠そうとした場合でもサーバ側に記録が残ります。複数機器の横断解析がしやすくなる点も利点です。集約してもログの発生件数は減らず、機器のディスクが増えるわけでもなく、時刻同期は依然として必要です。

</details>

## 3. 障害切り分けの手順（ping・traceroute）

「ネットにつながらない」と言われたとき、闇雲に設定を触るのではなく、**切り分け**で原因の範囲を狭めます。

### 切り分けの基本方針

- **下位層から順に**疑う: ケーブル・リンクランプ（物理層）→ IP設定・疎通（ネットワーク層）→ 名前解決・アプリの順
- **近いところから遠くへ**: 自分のPC → 同一LAN内 → デフォルトゲートウェイ → 外部、の順にpingで確認
- **切り分けの原則**: 「どこまでは正常か」を確定させながら、問題の範囲を狭めていく

### 代表的なコマンド

| コマンド | 仕組みと用途 |
|---|---|
| **ping** | ICMPのエコー要求/応答で、宛先までのIPレベルの疎通を確認する |
| **traceroute** | **TTLを1から1ずつ増やした**パケットを送り、各ルータが返すICMP時間超過メッセージで**経由するルータを順に特定**する |

### 典型パターン

「**IPアドレス指定のpingは通るのに、URL（ホスト名）ではつながらない**」——この場合、IPの経路は正常で、怪しいのは**名前解決（DNS）**です。このように「どの操作が成功し、どれが失敗したか」の組合せから原因の層を推定します。

> 💡 コツ: 🔴 午後試験では「次に何を確認すべきか」「この結果から何がいえるか」が記述で問われます。ping・tracerouteの結果を層に対応付けて説明できるようにしましょう。

### 確認問題

**問1.** PCからあるWebサイトを閲覧できない。WebサーバのIPアドレスを指定したpingは成功するが、URL（ホスト名）を指定するとアクセスも名前解決も失敗する。次に確認すべきことはどれか。

1. LANケーブルの断線の有無
2. デフォルトゲートウェイの電源状態
3. PCに設定されたDNSサーバのアドレスと、DNSサーバの稼働状態
4. WebサーバのIPアドレスの重複

<details><summary>答えと解説</summary>

正解: **3**

IP指定のpingが成功している時点で、物理層からネットワーク層までの経路は正常と確定します。失敗しているのはホスト名からIPアドレスへの変換なので、次に疑うのは名前解決（DNS設定とDNSサーバの稼働）です。ケーブルやゲートウェイに問題があればIP指定のpingも失敗するはずで、IPアドレス重複を最初に疑う状況でもありません。

</details>

**問2.** tracerouteが通信経路上のルータを順に特定できる仕組みとして、適切なものはどれか。

1. TTLを1から1ずつ増やしたパケットを送り、TTL切れを検出した各ルータが返すICMP時間超過メッセージを利用する
2. 各ルータのSNMPエージェントに経路情報を問い合わせる
3. ARP要求をブロードキャストして応答したルータを記録する
4. DNSサーバから経路上の全ルータの一覧を取得する

<details><summary>答えと解説</summary>

正解: **1**

tracerouteはTTL=1、2、3…と増やしながらパケットを送ります。TTLが0になった地点のルータはパケットを破棄してICMP時間超過メッセージを返すため、その送信元を見れば1ホップ目、2ホップ目…と経由ルータが順に分かります。SNMPやDNSへの問い合わせは使わず、ARPは同一セグメント内のアドレス解決にしか使えません。

</details>

**問3.** PCからインターネット上のサーバに接続できない。切り分けのため、まず自PCからデフォルトゲートウェイへpingを実行したところ失敗した。次に確認すべきことはどれか。

1. インターネット回線事業者の広域的な障害情報
2. 自PCのIPアドレス設定と、LANケーブルやリンクランプなどの接続状態
3. 外部DNSサーバの応答時間
4. Webサーバ側のアクセス制限設定

<details><summary>答えと解説</summary>

正解: **2**

デフォルトゲートウェイにすら届かないということは、問題は自PCから同一LAN内の範囲にある可能性が高いといえます。まず自PCのIP設定（アドレス・サブネットマスク・ゲートウェイ）と物理的な接続状態を確認します。回線事業者・外部DNS・Webサーバ側はいずれもゲートウェイより先の話で、LAN内の疎通が取れてから確認する対象です。

</details>

**問4.** 障害切り分けの進め方として、最も適切なものはどれか。

1. 最初に機器をすべて再起動してから原因を調べる
2. 利用者の申告があった時点で、まず機器の設定を変更してみる
3. 原因箇所の見当がつくまで、確認作業は行わない
4. 下位層や近い範囲から順に確認し、「どこまでは正常か」を確定させながら範囲を狭める

<details><summary>答えと解説</summary>

正解: **4**

切り分けの基本は、物理層などの下位層や自分に近い範囲から順に確認し、正常と確認できた範囲を除外しながら原因の範囲を狭めることです。原因が分からないまま再起動や設定変更をすると、証拠となる状態やログが失われたり、新たな障害を生んだりする恐れがあります。確認作業を先送りするのは論外です。

</details>

**問5.** pingコマンドが疎通確認に使用するプロトコルはどれか。

1. ICMP（エコー要求とエコー応答）
2. SMTP
3. SNMP
4. FTP

<details><summary>答えと解説</summary>

正解: **1**

pingはICMPのエコー要求を送り、エコー応答が返るかどうかで宛先までのIPレベルの疎通を確認します。SMTPはメール送信、SNMPは機器の監視・管理、FTPはファイル転送のプロトコルであり、いずれもpingの疎通確認に使われるものではありません。

</details>

## 4. 構成管理と変更管理（バックアップと世代管理）

ネットワーク障害の原因として常に上位に挙がるのが「**設定変更のミス**」です。それを防ぎ、起きても素早く戻すための仕組みが構成管理と変更管理です。

### 構成管理

- **構成情報の最新化**: ネットワーク構成図、IPアドレス管理台帳、機器一覧を常に実態と一致させます
- **設定（コンフィグ）のバックアップ**: 変更の**前後**に取得します。変更前のものは切り戻しに、変更後のものは機器故障時の復旧に使います
- **世代管理**: バックアップを上書きせず複数世代残します。「いつの変更で問題が入り込んだか」を特定でき、任意の時点の状態に戻せます

### 変更管理

設定変更は思いつきで行わず、**申請 → 影響範囲の評価 → 承認 → 実施 → 記録**という手順を踏みます。作業計画には次を含めます。

| 項目 | 内容 |
|---|---|
| 作業手順書 | 実施コマンドや確認項目を事前に明文化 |
| **切り戻し計画** | 失敗したときに元の状態へ戻す手順と判断基準 |
| メンテナンス時間帯 | 利用者への影響が小さい時間帯を選び、事前に周知 |

> 💡 コツ: ⚪ 優先度は低めですが、午後の運用問題で「作業前に何を準備すべきか」と問われたら「変更前コンフィグのバックアップと切り戻し計画」が鉄板の答えです。

### 確認問題

**問1.** ネットワーク機器の設定変更作業の前に準備しておくべきこととして、最も適切なものはどれか。

1. 変更後の設定が安定するまでログ取得を停止すること
2. 変更前の設定のバックアップ取得と、失敗時の切り戻し手順の準備
3. 作業を速くするために確認項目を省いた簡略手順書の用意
4. 障害に備えて利用者からの問合せ窓口を閉鎖すること

<details><summary>答えと解説</summary>

正解: **2**

変更作業の鉄則は「元に戻せる状態を作ってから触る」ことです。変更前のコンフィグのバックアップと、失敗時の切り戻し手順・判断基準をあらかじめ用意します。ログ取得の停止は障害解析の手がかりを失う行為で、確認項目の省略はミスのもと、問合せ窓口の閉鎖は影響の検知を遅らせるだけです。

</details>

**問2.** 設定バックアップを上書きせず複数世代保管する「世代管理」の利点として、最も適切なものはどれか。

1. バックアップに必要なディスク容量を削減できる
2. 設定変更そのものを自動化できる
3. どの時点の変更で問題が入り込んだかを特定し、任意の世代の状態へ戻せる
4. 機器のファームウェアを自動で最新化できる

<details><summary>答えと解説</summary>

正解: **3**

世代管理では過去の設定が時系列で残るため、世代間の差分からいつの変更で問題が混入したかを特定でき、必要なら数世代前の状態にも戻せます。複数世代を残す分だけ容量はむしろ増えますし、世代管理自体に設定変更の自動化やファームウェア更新の機能はありません。

</details>

**問3.** 変更管理のプロセスとして、最も適切なものはどれか。

1. 変更の申請と影響範囲の評価を行い、承認を得てから計画した時間帯に実施し、結果を記録する
2. 緊急性にかかわらず、気付いた担当者がその場で設定を変更して事後報告する
3. 影響の小さい変更は記録を残さずに実施する
4. 変更作業はすべて利用者の多い日中に行い、問題の発生に気付きやすくする

<details><summary>答えと解説</summary>
