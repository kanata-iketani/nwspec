# 第15章 DNS

ドメイン名から IP アドレスを引く DNS の章です。ルートから権威サーバへたどる名前解決の流れ、キャッシュと TTL、リソースレコードの種類、そしてキャッシュポイズニングなどのセキュリティまで、午前Ⅱ・午後ともに出題率の高い分野を学びます。

## 1. 名前解決のしくみ（階層構造・ルートから辿る流れ）

私たちは www.example.jp のような**ドメイン名**でサーバを指定しますが、実際の通信には IP アドレスが必要です。この変換（**名前解決**）を担う分散データベースが **DNS** です。

### ドメイン名は階層構造

ドメイン名は右端ほど上位で、**ルート（.）→ jp → example → www** という木構造になっています。各階層の情報は、その階層を正式に管理する**権威 DNS サーバ**が持ち、上位のサーバは「その先はこの権威サーバに聞いて」という**委任情報**だけを知っています。

### www.example.jp を解決する流れ

1. PC は、設定された**キャッシュ DNS サーバ（フルサービスリゾルバ）**に「www.example.jp の IP アドレスは？」と聞く
2. キャッシュサーバは、まず**ルートサーバ**に聞く →「jp のことは jp の権威サーバへ」と委任先を教えられる
3. **jp の権威サーバ**に聞く →「example.jp のことは example.jp の権威サーバへ」
4. **example.jp の権威サーバ**に聞く → ついに IP アドレス（答え）が返る
5. キャッシュサーバが答えを PC に返す

答えは一定時間保存され、2回目以降は即答できます。

### 権威サーバとキャッシュサーバ

| 種類 | 役割 |
|---|---|
| 権威サーバ | 自分が管理するゾーンの正式な情報を持つ「台帳」 |
| キャッシュサーバ | PC の代わりに解決して回り、結果を保存する「代理人」 |

> 💡 コツ：🔴「上位は委任先しか知らない。だからルートから1段ずつ下りる」——この流れを自分の言葉で説明できることが DNS 全体の土台です。

### 確認問題

**問1.** キャッシュに何も情報がない状態のキャッシュ DNS サーバが www.example.jp の名前解決を始めるとき、最初に問い合わせる相手はどれでしょう？

1. example.jp の権威サーバ
2. www.example.jp の Web サーバ本体
3. ルートサーバ
4. jp の権威サーバ

<details><summary>答えと解説</summary>

正解: **3**

手がかりが何もないとき、キャッシュサーバは階層の頂点であるルートサーバから辿り始め、「jp は jp の権威サーバへ」という委任をもらって1段ずつ下ります。jp や example.jp の権威サーバの所在はルートから辿って初めて分かるため最初には聞けず、Web サーバ本体は名前解決に答える立場ではありません。

</details>

**問2.** 権威 DNS サーバとキャッシュ DNS サーバ（フルサービスリゾルバ）の違いとして、正しいものはどれでしょう？

1. 権威サーバは自分が管理するゾーンの正式な情報を持ち、キャッシュサーバはクライアントの代わりに解決して結果を保存する
2. 権威サーバは社内専用、キャッシュサーバはインターネット専用である
3. 両者は同じ機能で、設置場所だけが違う
4. キャッシュサーバがゾーンの正式な情報を管理し、権威サーバはその複製を持つ

<details><summary>答えと解説</summary>

正解: **1**

権威サーバはゾーン情報の「台帳」そのもので、キャッシュサーバは PC に代わってルートから解決して回り、得た答えを保存して再利用する「代理人」です。役割が逆の説明は誤りで、両者は機能そのものが異なります。設置場所（社内かインターネットか）で区別されるものでもありません。

</details>

**問3.** キャッシュ DNS サーバがルートサーバから順に権威サーバを辿って答えに到達できるのはなぜでしょう？

1. ルートサーバが世界中の全ドメインの IP アドレスを記憶しているから
2. キャッシュサーバに全権威サーバの一覧があらかじめ全件登録されているから
3. 権威サーバ同士が常に全情報を複製し合っているから
4. 各階層の権威サーバが、1つ下の階層の権威サーバへの委任情報を返してくれるから

<details><summary>答えと解説</summary>

正解: **4**

DNS は分散データベースで、各階層は「その先の管理はこのサーバに任せた」という委任情報（下位の NS）だけを持ちます。これを順に教えてもらうことで、ルートから答えを持つ権威サーバまで辿り着けます。ルートサーバが全ドメインの答えを持つわけではなく、キャッシュサーバが事前に全一覧を持つことも、全権威サーバが相互に全複製を持つこともありません。

</details>

**問4.** ドメイン名 www.example.jp の階層構造について、正しい説明はどれでしょう？

1. 左端の www が最上位で、右へ行くほど下位になる
2. 右端に近い jp ほど上位で、頂点にはルート（.）がある
3. www・example・jp はすべて同格で、階層関係はない
4. 最上位は example で、jp と www がその下位である

<details><summary>答えと解説</summary>

正解: **2**

ドメイン名は右端ほど上位の木構造で、頂点のルートの下に jp（トップレベルドメイン）、その下に example、さらにその下に www と続きます。名前解決で「ルート → jp → example.jp」の順に辿るのはこの構造のためです。左端が上位という理解や、階層がない・example が頂点という理解では、問い合わせの順序を説明できません。

</details>

## 2. 再帰問い合わせと反復問い合わせ・キャッシュ・TTL

前チャプターの名前解決の流れには、性質の違う2種類の問い合わせが混ざっていました。

### 再帰と反復

| 種類 | 区間 | 意味 |
|---|---|---|
| **再帰問い合わせ** | PC → キャッシュサーバ | 「最終的な答えが出るまで全部任せます」 |
| **反復問い合わせ** | キャッシュサーバ → 各権威サーバ | 「知っている範囲（委任先）を教えて。次は自分で聞きに行きます」 |

PC は1回聞いて待つだけ、キャッシュサーバはルート → jp → example.jp と**自分の足で回る**、という分担です。権威サーバは答えか委任先を返すだけで、代わりに調べ回ることはしません。

### キャッシュと TTL

キャッシュサーバは得た答えを **TTL（Time To Live）**秒だけ保存します。TTL は**その情報を管理する権威サーバ側がレコードごとに設定**する値で、キャッシュが生きている間は上位に聞きに行かないため、応答が速くなりサーバの負荷も減ります。

- **TTL を長くする**：問い合わせが減り負荷に強いが、情報の変更が世界に行き渡るまで時間がかかる
- **TTL を短くする**：変更の反映は速いが、問い合わせ回数が増える

このため実務では、**サーバの IP アドレスを変更（移転）する前に、あらかじめ TTL を短くしておく**のが定石です。古い情報のキャッシュが早く消え、切替がスムーズになります。

> 💡 コツ：🔴「再帰 = 丸投げ、反復 = 委任先をもらって自分で回る」。午後では TTL と切替時間の関係が、理由を記述させる形で問われます。

### 確認問題

**問1.** DNS の再帰問い合わせの説明として、正しいものはどれでしょう？

1. 権威サーバが委任先の情報だけを返す問い合わせ方式
2. クライアントがキャッシュサーバに対し、最終的な答えを得るまでの処理を任せる問い合わせ方式
3. 同じ問い合わせを一定間隔で繰り返し再送する方式
4. キャッシュサーバがルートサーバから順に自分で辿っていく方式

<details><summary>答えと解説</summary>

正解: **2**

再帰問い合わせは「答えが出るまでお任せします」という依頼で、PC からキャッシュサーバへの問い合わせがこれに当たります。キャッシュサーバが委任先をもらいながら自分で権威サーバを辿っていくのは反復問い合わせです。委任先だけを返すのは反復問い合わせを受けた権威サーバ側の応答であり、再送の繰り返しは問い合わせ方式の分類とは関係ありません。

</details>

**問2.** 反復問い合わせを受けたルートサーバが www.example.jp について返すものはどれでしょう？

1. www.example.jp の IP アドレスそのもの
2. キャッシュサーバに代わって example.jp まで調べた最終結果
3. 「分からない」というエラー応答
4. jp を管理する権威サーバの情報（委任先）

<details><summary>答えと解説</summary>

正解: **4**

ルートサーバは各トップレベルドメインの委任先しか知らないため、「jp のことは jp の権威サーバへ」と教え、続きはキャッシュサーバ自身が聞きに行きます。ルートサーバが最終的な IP アドレスを知っているわけではなく、代わりに調べ回ること（再帰的な処理）もしません。委任先を案内できる以上、エラーにもなりません。

</details>

**問3.** Web サーバの IP アドレスを変更する作業の前に、該当レコードの TTL をあらかじめ短くしておくのはなぜでしょう？

1. 世界中のキャッシュサーバに残る古い情報が早く期限切れになり、新しい IP アドレスへの切替が速く行き渡るから
2. TTL を短くすると DNS の応答パケットが小さくなり通信が速くなるから
3. TTL を短くしないと権威サーバがレコードを更新できないから
4. TTL が短いほどキャッシュサーバへの問い合わせ回数が減るから

<details><summary>答えと解説</summary>

正解: **1**

キャッシュは TTL 秒間残り続けるため、TTL が長いままだと変更後も古い IP アドレスが世界中で参照され続けます。事前に TTL を短くしておけば古いキャッシュが早く消え、切替がスムーズになります。TTL は応答パケットの大きさを変えるものではなく、権威サーバの更新可否とも無関係です。また TTL を短くすると問い合わせはむしろ増えます。

</details>

**問4.** レコードの TTL を長く設定した場合の効果として、正しいものはどれでしょう？

1. レコードの変更が即座に全キャッシュサーバへ通知されるようになる
2. キャッシュが禁止され、毎回権威サーバに問い合わせるようになる
3. キャッシュが長持ちして問い合わせ回数と権威サーバの負荷が減る一方、変更の反映には時間がかかる
4. 名前解決の結果の信頼性が暗号学的に保証される

<details><summary>答えと解説</summary>

正解: **3**

TTL が長いほどキャッシュの再利用が増えて応答は速く、権威サーバの負荷も減りますが、その分だけ古い情報が残る時間も延び、変更の反映が遅くなります。これはトレードオフの関係です。DNS に変更を各キャッシュへ即時通知する仕組みはなく、キャッシュ禁止は TTL を長くする効果の逆です。応答の信頼性を暗号的に保証するのは DNSSEC の役割です。

</details>

## 3. リソースレコード（A・AAAA・CNAME・MX・NS・PTR・TXT）

権威サーバが管理する1件1件の情報を**リソースレコード**といいます。種類（タイプ）ごとの役割を覚えましょう。

### 主なリソースレコード

| タイプ | 内容 |
|---|---|
| **A** | ドメイン名 → **IPv4 アドレス** |
| **AAAA** | ドメイン名 → **IPv6 アドレス** |
| **CNAME** | 別名 → 正式名（エイリアス） |
| **MX** | そのドメイン**宛メールの配送先**メールサーバ |
| **NS** | そのゾーンの権威サーバ（委任情報） |
| **PTR** | **IP アドレス → ドメイン名（逆引き）** |
| **TXT** | 任意のテキスト。**SPF**（送信元メールサーバの正当性確認）などに利用 |
| SOA | ゾーンの管理情報（管理者・シリアル番号など） |

### 試験で狙われるポイント

- **MX にはプリファレンス値**が付き、**小さいほうが優先**されます。「MX 10 と MX 20 なら、まず 10 のサーバへ配送し、だめなら 20 へ」という優先順位です
- **CNAME** は「www.example.jp の実体は server1.example.jp です」のような別名定義です。別名を引いたクライアントは、正式名をあらためて解決して IP アドレスに到達します
- **PTR** は逆引き用で、迷惑メール対策として「送信元 IP を逆引きできるか」の確認などに使われます

> 💡 コツ：🔴 午後の設問では「メールが届かない → まず MX レコードを疑う」「別名でアクセスさせたい → CNAME」のように、**症状や要件からレコード名を即答**できることが求められます。表を白紙に書き出せるまで繰り返しましょう。

### 確認問題

**問1.** example.jp 宛の電子メールをどのメールサーバに配送すべきかを調べるときに参照するリソースレコードはどれでしょう？

1. MX レコード
2. A レコード
3. PTR レコード
4. NS レコード

<details><summary>答えと解説</summary>

正解: **1**

MX（Mail eXchange）レコードは、そのドメイン宛メールの配送先メールサーバを示す専用のレコードです。送信側のメールサーバはまず MX を引き、得られたサーバ名を A レコードで IP アドレスに解決して配送します。A は名前から IPv4 アドレス、PTR は逆引き、NS は権威サーバの委任情報で、配送先の決定には使いません。

</details>

**問2.** あるドメインに「MX 10 mail1.example.jp」「MX 20 mail2.example.jp」の2つのレコードが登録されています。メールの配送先の扱いとして正しいものはどれでしょう？

1. 値の大きい mail2 が常に優先される
2. 2台へ同じメールが同時に配送される
3. 値の小さい mail1 が優先され、接続できないときに mail2 が使われる
4. ドメイン名のアルファベット順で配送先が決まる

<details><summary>答えと解説</summary>

正解: **3**

MX のプリファレンス値は小さいほうが優先なので、通常は 10 の mail1 に配送し、障害などで接続できない場合に 20 の mail2 を使います。これによりバックアップのメールサーバを用意できます。大きい値が優先という逆の理解は典型的なひっかけで、同時配送やアルファベット順という仕様もありません。

</details>

**問3.** CNAME レコードの役割として、正しいものはどれでしょう？

1. ドメイン名に対応する IPv6 アドレスを登録する
2. ある名前が別の正式名の別名（エイリアス）であることを定義する
3. ゾーンの管理者情報とシリアル番号を保持する
4. ドメインの所有者を証明する電子署名を格納する

<details><summary>答えと解説</summary>

正解: **2**

CNAME は「この名前の実体はこちらの正式名です」という別名定義で、引いたクライアントは正式名を改めて解決して IP アドレスに到達します。サービス名（www など）と実サーバ名を分けて管理したいときに便利です。IPv6 アドレスの登録は AAAA、ゾーンの管理情報は SOA の役割で、電子署名は DNSSEC 関連のレコードが扱います。

</details>

**問4.** IP アドレスからドメイン名を調べる「逆引き」に使うリソースレコードはどれでしょう？

1. TXT レコード
2. AAAA レコード
3. CNAME レコード
4. PTR レコード

<details><summary>答えと解説</summary>

正解: **4**

PTR レコードは IP アドレスからドメイン名を引く逆引き専用のレコードで、迷惑メール対策として送信元 IP アドレスの逆引き確認などに使われます。AAAA は名前から IPv6 アドレスを引く正引き、CNAME は別名定義、TXT は SPF などに使う自由記述のテキストであり、逆引きの機能はありません。

</details>

## 4. DNS のセキュリティ（キャッシュポイズニング・DNSSEC・オープンリゾルバ）

DNS の応答は基本的に UDP の平文で、**「先に届いた、それらしい応答」を信じてしまう**性質があります。ここを突く攻撃と対策を押さえましょう。

### キャッシュポイズニング

攻撃者は、キャッシュサーバが権威サーバに問い合わせた直後を狙い、**本物より先に偽の応答を送り込んで、偽の IP アドレスをキャッシュさせます**。成功すると、そのキャッシュサーバを使う全ユーザーが、正しいドメイン名を入力しても**偽サイトへ誘導**されてしまいます。偽装には問い合わせの ID（16ビット）とポート番号を当てる必要があるため、**送信元ポートのランダム化**で当てにくくするのが基本対策です。

### DNSSEC

根本対策が **DNSSEC** です。権威サーバがレコードに**ディジタル署名**を付け、受け取った側が検証することで、**応答が正当な管理者のもので、改ざんされていないこと**（出自と完全性）を確認できます。注意点は、**暗号化して盗聴を防ぐ仕組みではない**ことです。

### オープンリゾルバ

誰からの再帰問い合わせにも答えるキャッシュサーバを**オープンリゾルバ**といいます。これを放置すると、**送信元 IP を標的に詐称した小さな問い合わせ**に対する**大きな応答**が標的に集中する **DNS リフレクション（アンプ）攻撃**の踏み台にされます。対策は、再帰問い合わせに応答する範囲を自組織内に限定することです。

> 💡 コツ：🟡 3つとも「DNS は応答を疑わない」という弱点から派生しています。午後では「なぜ踏み台になるのか」を増幅・反射の言葉で説明させる問題が出ます。

### 確認問題

**問1.** DNS キャッシュポイズニング攻撃の狙いとして、最も適切なものはどれでしょう？

1. キャッシュサーバのディスクを偽データで満杯にして停止させること
2. 権威サーバの管理者パスワードを窃取すること
3. TTL を改ざんしてキャッシュを永続化すること
4. キャッシュサーバに偽の応答を記憶させ、利用者を正規のドメイン名のまま偽サイトへ誘導すること

<details><summary>答えと解説</summary>

正解: **4**

キャッシュポイズニングは、本物の応答より先に偽の応答を送り込んで偽の IP アドレスをキャッシュさせる攻撃で、成功するとそのキャッシュサーバの全利用者が正しい URL を入力しても偽サイトに接続されてしまいます。ディスクの圧迫やパスワード窃取が目的ではなく、TTL の改ざん自体が狙いでもありません。

</details>

**問2.** DNSSEC が提供する機能として、正しいものはどれでしょう？

1. DNS の問い合わせと応答をすべて暗号化して盗聴を防ぐ
2. ディジタル署名の検証により、応答が正当な権威サーバ由来で改ざんされていないことを確認できる
3. キャッシュサーバの応答速度を向上させる
4. 不正な利用者からの問い合わせを認証して遮断する

<details><summary>答えと解説</summary>

正解: **2**

DNSSEC は権威サーバがレコードに付けたディジタル署名を検証する仕組みで、応答の出自の正当性と完全性（改ざんされていないこと）を保証し、キャッシュポイズニング対策になります。通信の暗号化（盗聴防止）は行わない点が最大のひっかけどころです。署名の検証処理が加わるため高速化の仕組みでもなく、問い合わせ元の利用者を認証する機能もありません。

</details>

**問3.** オープンリゾルバを放置してはいけない理由として、最も適切なものはどれでしょう？

1. 送信元 IP アドレスを標的に詐称した問い合わせに大きな応答を返してしまい、DNS リフレクション（アンプ）攻撃の踏み台にされるから
2. 再帰問い合わせを一切処理できなくなるから
3. キャッシュの TTL を設定できなくなるから
4. 権威サーバとしてゾーン情報を公開できなくなるから

<details><summary>答えと解説</summary>

正解: **1**

オープンリゾルバは誰の問い合わせにも答えるため、攻撃者が送信元を標的の IP アドレスに詐称して小さな問い合わせを送ると、何倍にも増幅された応答が標的へ集中します（リフレクション + 増幅）。対策は再帰問い合わせへの応答を自組織内に限定することです。再帰処理ができないのではなく「できすぎる」ことが問題で、TTL 設定や権威サーバとしての公開機能とは関係ありません。

</details>

**問4.** キャッシュポイズニング攻撃を成功しにくくする対策として、適切なものはどれでしょう？

1. レコードの TTL をすべて 0 に設定する
2. キャッシュサーバを停止し、各 PC がルートサーバへ直接問い合わせる
3. 問い合わせの送信元ポート番号をランダム化し、偽応答が正しい ID とポートを当てにくくする
4. DNS の利用を TCP から UDP に切り替える

<details><summary>答えと解説</summary>

正解: **3**

攻撃者が偽応答を受け入れさせるには問い合わせ ID と送信元ポートを一致させる必要があるため、ポートをランダム化すると総当たりの成功率が大きく下がります。TTL を 0 にするとキャッシュの利点を失ううえ問い合わせが激増します。全 PC がルートへ直接問い合わせる構成は非現実的で負荷の面でも不適切です。DNS はもともと主に UDP を使っており、切り替えは対策になりません。

</details>
