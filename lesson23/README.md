# 第23章 高信頼設計（冗長化・負荷分散）

機器は必ず壊れる前提で、「壊れても止まらない」ネットワークを設計する章です。単一障害点の見つけ方から、VRRP やスタックによる機器の冗長化、負荷分散装置、サイトをまたぐ冗長化と DR までを学びます。

## 1. 冗長化の考え方（単一障害点をなくす・アクティブ/スタンバイ）

機器や回線は**必ずいつか壊れる**という前提に立ち、壊れてもサービスを止めない設計を**冗長化**と呼びます。

### まず単一障害点（SPOF）を探す

**単一障害点（SPOF：Single Point of Failure）**とは、そこが故障するとシステム全体が止まってしまう箇所です。冗長化の第一歩は、構成図を端から端まで目で追い、「この1台（1本）が壊れたら通信は続くか？」を全要素について確認することです。FW を2台にしても、その先のスイッチが1台なら SPOF は残っています。

### 2つの冗長化スタイル

| 方式 | 動き方 | ポイント |
|---|---|---|
| アクティブ/スタンバイ | 1台が稼働し、もう1台は待機。障害時に待機系へ**フェールオーバー** | 普段は待機系の性能が遊ぶ。切り替え後に元へ戻すのが**フェールバック** |
| アクティブ/アクティブ | 全台が同時に稼働して負荷を分担 | 1台壊れても**残りで全トラフィックを処理できる容量**で設計する必要がある |

障害に気づく仕組みも不可欠です。相手の生存確認（**ヘルスチェック・死活監視**）が途絶えたことをきっかけに、自動で切り替えが起こります。

> 💡 コツ：午後の構成図問題では「箱と線を1つずつ指差して、壊れたらどうなるかを言ってみる」のが SPOF 発見の最短ルートです。

🔴 「SPOF はどこか」「切り替わる仕組みは何か」は午後Ⅰ・Ⅱの最頻出テーマです。この章の見方を体に染み込ませましょう。

### 確認問題

**問1.** 単一障害点（SPOF）の説明として、適切なものはどれでしょう？

1. 障害が1回しか発生しない、信頼性の高い箇所のこと
2. 最も負荷が高くなる箇所のこと
3. そこが故障するとシステム全体が停止してしまう、冗長化されていない箇所のこと
4. 障害発生時に最初にログが記録される機器のこと

<details><summary>答えと解説</summary>

正解: **3**

SPOF は「ここが壊れたら全体が止まる」という代替手段のない箇所を指し、冗長化設計ではまずこれを洗い出して潰します。障害が1回しか起きない箇所という意味ではなく、負荷の高さやログの記録順とも関係ありません。

</details>

**問2.** アクティブ/スタンバイ構成の「フェールオーバー」の説明として、適切なものはどれでしょう？

1. 稼働系の障害を検知した際に、待機系が処理を引き継ぐこと
2. 定期メンテナンスのために両系を同時に停止すること
3. 待機系を撤去してコストを削減すること
4. 復旧した元の稼働系に処理を戻すこと

<details><summary>答えと解説</summary>

正解: **1**

フェールオーバーは、障害検知をきっかけに待機系へ処理を自動で引き継ぐ動作です。これにより利用者から見たサービス停止を最小限にできます。復旧後に元の系へ処理を戻す操作はフェールバックと呼ばれる別の動作です。両系の同時停止や待機系の撤去は冗長化の目的と逆行する行為です。

</details>

**問3.** アクティブ/アクティブ構成で2台の機器に負荷を分散する場合、容量設計上の注意点として最も適切なものはどれでしょう？

1. 2台の合計が通常負荷ぴったりになるように設計する
2. 待機系の機器は電源を切っておく
3. 2台のうち性能の低いほうに全トラフィックを集中させる
4. 1台に障害が起きても、残った1台だけで全トラフィックを処理できる容量にしておく

<details><summary>答えと解説</summary>

正解: **4**

アクティブ/アクティブでは普段2台で分担している負荷が、障害時には残る1台に集中します。そのため各機器は単独で全体を処理できる余裕を持たせて設計しないと、障害時に過負荷で共倒れになります。合計が通常負荷ぴったりでは障害時に足りません。全台が稼働するのがこの方式なので電源を切る待機系は存在せず、低性能側へ意図的に集中させる理由もありません。

</details>

**問4.** インターネット回線と FW をそれぞれ2系統に冗長化しましたが、FW の内側にある L2 スイッチは1台のままで、全サーバがそのスイッチに接続されています。この構成の弱点はどこでしょう？

1. FW を2台にしたこと自体が通信の妨げになる
2. L2 スイッチが単一障害点として残っており、故障すると全サーバへの通信が止まる
3. インターネット回線が2系統あるとルーティングが必ず破綻する
4. サーバをスイッチに接続していること

<details><summary>答えと解説</summary>

正解: **2**

回線と FW を冗長化しても、全サーバの通信が必ず通る L2 スイッチが1台なら、そこが壊れた時点で全サーバが孤立します。冗長化は経路上のすべての要素で考える必要があります。FW の冗長化や回線の2系統化は適切な設計であり、それ自体が通信を妨げたり経路制御を破綻させたりするものではありません。サーバをスイッチに接続するのはごく普通の構成です。

</details>

## 2. 機器の冗長化（VRRP 復習・スイッチのスタック・リンク冗長）

### VRRP：デフォルトゲートウェイの冗長化（復習）

**VRRP** は、複数のルータで1つの**仮想ルータ**を構成する仕組みです。PC のデフォルトゲートウェイには**仮想 IP アドレス**を設定しておきます。普段は優先度の高い**マスタ**が仮想 IP 宛ての通信を処理し、定期的に **VRRP 広告**を送って生存を知らせます。広告が一定時間途絶えると**バックアップ**がマスタに昇格します。仮想 IP（と仮想 MAC）をそのまま引き継ぐため、**PC 側の設定変更は一切不要**で切り替わるのが最大のポイントです。

### スタック：スイッチを論理的に1台へ

**スタック**は、複数の物理スイッチを専用ケーブルなどで束ね、論理的に1台のスイッチとして動かす技術です。設定・管理が一元化できるうえ、**2台の物理スイッチにまたがるリンクアグリゲーション**を組めるため、STP のようにリンクを遊ばせることなく、機器とリンクの両方を冗長化できます。

### リンク冗長：LAG

**リンクアグリゲーション（LAG）**は複数の物理リンクを1本の論理リンクに束ねる技術で、帯域を合算しつつ、1本切れても残りで通信を継続できます（ネゴシエーションには LACP を使用）。

> 💡 コツ：「ゲートウェイは VRRP、スイッチ本体はスタック、ケーブルは LAG」。何を冗長化する技術かで整理しましょう。

🔴 「マスタ障害時に何をきっかけに、どこまで自動で切り替わるか」を自分の言葉で言えるようにしましょう。午後で確実に効きます。

### 確認問題

**問1.** VRRP を使う場合、配下の PC のデフォルトゲートウェイにはどのアドレスを設定するでしょう？

1. マスタルータの物理 IP アドレス
2. バックアップルータの物理 IP アドレス
3. 仮想ルータの仮想 IP アドレス
4. DNS サーバの IP アドレス

<details><summary>答えと解説</summary>

正解: **3**

PC には仮想 IP アドレスを設定します。マスタが故障してもバックアップが同じ仮想 IP（と仮想 MAC）を引き継ぐため、PC は何も変更せずに通信を続けられます。マスタやバックアップの物理 IP を設定すると、その機器の故障時に手動変更が必要になり冗長化の意味がなくなります。DNS サーバのアドレスは名前解決用でゲートウェイ設定とは別物です。

</details>

**問2.** VRRP でバックアップルータがマスタの障害を検知する仕組みはどれでしょう？

1. マスタから定期的に送られる VRRP 広告が、一定時間届かなくなったことで検知する
2. 利用者が障害を電話で連絡する
3. マスタが故障の直前に「これから壊れます」という通知を送る
4. バックアップが毎回マスタに ping を送って応答時間を測定する

<details><summary>答えと解説</summary>

正解: **1**

マスタは定期的に VRRP 広告（advertisement）を送信しており、バックアップはこれが一定時間途絶えたことをもってマスタの障害と判断し、自動でマスタに昇格します。人手の連絡を待つ仕組みではありません。機器は故障を予告できませんし、VRRP の標準の検知手段はバックアップからの ping ではなく広告の受信監視です。

</details>

**問3.** スイッチをスタック構成にする利点として、最も適切なものはどれでしょう？

1. スイッチの消費電力が半分になる
2. VLAN を使う必要がなくなる
3. ブロードキャストが一切発生しなくなる
4. 2台の物理スイッチにまたがるリンクアグリゲーションを組め、STP に頼らず機器とリンクの両方を冗長化できる

<details><summary>答えと解説</summary>

正解: **4**

スタックで論理的に1台となったスイッチには、サーバや対向スイッチから2台それぞれへケーブルを伸ばして1つの LAG を組めます。これにより片方のスイッチやリンクが故障しても通信が続き、STP のようにリンクをブロックして遊ばせることもありません。消費電力が半減する効果はなく、VLAN の必要性やブロードキャストの発生はスタックとは別の話です。

</details>

**問4.** リンクアグリゲーション（LAG）の説明として、適切なものはどれでしょう？

1. 1本の物理リンクを複数の論理リンクに分割する技術である
2. 複数の物理リンクを1本の論理リンクに束ね、帯域の拡大と障害時の継続を両立する技術である
3. ループを検出してポートをブロックする技術である
4. ルータ同士で経路情報を交換する技術である

<details><summary>答えと解説</summary>

正解: **2**

LAG は複数の物理リンクを論理的に1本として扱い、帯域を合算しながら、1本が切断されても残りのリンクで通信を継続できます（ネゴシエーションには LACP を使います）。1本を分割するのではなく複数を束ねる技術です。ループ検出とブロックは STP、経路情報の交換は OSPF や BGP などルーティングプロトコルの役割です。

</details>

## 3. 負荷分散装置（LB の方式・ヘルスチェック・セッション維持）

**負荷分散装置（LB：ロードバランサ）**は、クライアントからのリクエストを複数のサーバに振り分ける装置です。処理能力の拡大（スケールアウト）と、サーバ障害時の切り離しによる可用性向上を同時に実現します。

### 振り分け方式

| 方式 | 動き |
|---|---|
| ラウンドロビン | 順番に均等に振り分ける |
| 最少コネクション | 現在のコネクション数が最も少ないサーバへ |
| 重み付け | 性能の高いサーバに多めに振る |

### ヘルスチェック：壊れたサーバを外す

LB は定期的にサーバの生存を確認し、応答しないサーバを振り分け対象から自動で外します。確認する深さに段階があり、**L3**（ping）は機器の生存のみ、**L4**（TCP 接続）はポートの応答まで、**L7**（HTTP リクエストを送り応答コードを確認）は**アプリケーションが正常に動いているか**まで確認できます。「OS は生きているのにアプリだけ異常」という障害は L7 でないと検知できません。

### セッション維持（パーシステンス）

ログイン状態や買い物かごは特定サーバが保持していることが多いため、同じ利用者のリクエストは**同じサーバに送り続ける**必要があります。送信元 IP アドレスで固定する方式や、**Cookie** を使う方式があります。

> 💡 コツ：LB の設問は「どう振るか・壊れたらどう外すか・同じ人をどう固定するか」の3点セットで整理しましょう。

🔴 ヘルスチェックの L3/L4/L7 の違いは、午後で「なぜこの障害を検知できなかったか」という形で問われる最重要ポイントです。

### 確認問題

**問1.** 負荷分散方式のうち「最少コネクション方式」の説明として、適切なものはどれでしょう？

1. すべてのサーバに同じリクエストを同時に送る
2. 接続してきた順にサーバを1台ずつ順番に割り当てる
3. 送信元 IP アドレスのハッシュ値だけで振り分け先を決める
4. その時点でコネクション数が最も少ないサーバへ新しいリクエストを振り分ける

<details><summary>答えと解説</summary>

正解: **4**

最少コネクション方式は、現在処理中のコネクション数が最も少ない、つまり最も空いているサーバを選ぶ方式で、処理時間にばらつきがある場合に負荷を平準化しやすいのが利点です。順番に割り当てるのはラウンドロビン、送信元 IP のハッシュで決めるのは別の固定的な方式です。全サーバに同じリクエストを同時に送るのは負荷分散ではなく無駄な複製です。

</details>

**問2.** L7（HTTP）ヘルスチェックが L3（ping）ヘルスチェックより優れている点はどれでしょう？

1. OS は稼働しているが Web アプリケーションがエラーを返すような障害まで検知できる
2. ネットワーク帯域をまったく消費しない
3. サーバの電源が入っているかだけを高速に確認できる
4. チェックの設定が最も簡単である

<details><summary>答えと解説</summary>

正解: **1**

L7 ヘルスチェックは実際に HTTP リクエストを送って応答コードや内容を確認するため、「ping には応答するがアプリは異常」という障害を検知して切り離せます。チェック自体が通信を行うので帯域消費ゼロではありません。電源や機器の生存確認だけなら L3 で足り、設定の単純さも L3 のほうが上なので、L7 の利点は検知の深さにあります。

</details>

**問3.** LB でセッション維持（パーシステンス）が必要になる理由として、適切なものはどれでしょう？

1. サーバの台数を減らすため
2. すべての利用者を1台のサーバに集約するため
3. ログイン状態や買い物かごなどの情報を特定のサーバが保持しており、同じ利用者を同じサーバへ送り続けないと状態が失われるため
4. ヘルスチェックの回数を減らすため

<details><summary>答えと解説</summary>

正解: **3**

セッション情報をサーバ側で保持する構成では、途中で別のサーバに振り分けられるとログイン状態などが引き継がれず、利用者から見ると突然ログアウトしたような動きになります。これを防ぐのがパーシステンスです。全利用者を1台に集約したら負荷分散になりません。サーバ台数の削減やヘルスチェック回数の削減が目的の機能でもありません。

</details>

**問4.** 送信元 IP アドレスによるセッション維持を使う構成で、多数の社員が NAPT 装置を経由して社外の Web サービスにアクセスする場合に起こる問題はどれでしょう？

1. 社員ごとに毎回異なるサーバへ振り分けられてセッションが切れる
2. 全社員の送信元が同じグローバル IP アドレスに見えるため、特定の1台のサーバへアクセスが集中して負荷分散が機能しない
3. NAPT 装置がヘルスチェックに応答してしまい、サーバ障害を検知できない
4. Cookie が暗号化されて読めなくなる

<details><summary>答えと解説</summary>

正解: **2**

NAPT 配下の端末は外部からはすべて同じグローバル IP に見えるため、送信元 IP で固定する方式では全社員が同じサーバへ振られ、負荷が偏ります。この場合は Cookie 方式のパーシステンスが有効です。同一 IP に見える以上「毎回異なるサーバへ」はむしろ起こりません。NAPT 装置がサーバの代わりにヘルスチェックへ応答することはなく、Cookie の暗号化もこの構成が原因で起こる事象ではありません。

</details>

## 4. サイト冗長と DR（DNS ラウンドロビン・GSLB・バックアップサイト）

機器単位の冗長化だけでは、データセンター全体の被災や停電には対抗できません。**サイト（拠点）単位の冗長化**を考えます。

### DNS ラウンドロビン：手軽だが弱点あり

1つのドメイン名に複数サーバの A レコードを登録し、DNS が応答のたびに順番を変えて返す方式です。装置いらずで手軽ですが、DNS サーバは**サーバの生死を知らない**ため、**故障したサーバの IP アドレスもそのまま返してしまう**のが致命的な弱点です。

### GSLB：ヘルスチェックと連動する DNS

**GSLB（広域負荷分散）**は、DNS の仕組みに各サイトへの**ヘルスチェック**を組み合わせ、**正常なサイトの IP アドレスだけを応答する**仕組みです。東京サイトがダウンしたら、名前解決の時点で大阪サイトの IP だけを返すため、利用者は自然に生きているサイトへ誘導されます。切り替えを早く効かせるため、DNS 応答の **TTL は短く**設定します（TTL が長いとキャッシュが残り、利用者が旧サイトへアクセスし続けてしまいます）。

### DR とバックアップサイト

災害からの復旧計画（**DR**）では、待機サイトを準備レベルで分けます。

| 種類 | 状態 | 復旧 | コスト |
|---|---|---|---|
| ホットサイト | 本番同等の設備が常時稼働 | 即時 | 高 |
| ウォームサイト | 機器はあるが一部のみ稼働 | 数時間〜数日 | 中 |
| コールドサイト | 場所と設備枠のみ確保 | 数日〜数週間 | 低 |

🟡 「DNS ラウンドロビンの弱点は？」→「障害サーバを応答から除外できない」、その解決が GSLB。この流れで覚えましょう。

### 確認問題

**問1.** DNS ラウンドロビンによる負荷分散の弱点として、最も適切なものはどれでしょう？

1. 専用の高価な装置を各サイトに設置する必要がある
2. DNS サーバはサーバの生死を把握していないため、故障したサーバの IP アドレスも利用者に返してしまう
3. 2台までのサーバにしか振り分けられない
4. ドメイン名を利用者が覚えられなくなる

<details><summary>答えと解説</summary>

正解: **2**

DNS ラウンドロビンは登録された A レコードを機械的に順繰りに返すだけで、ヘルスチェックを行いません。そのため障害中のサーバの IP も返され、一部の利用者は接続に失敗します。この弱点を解決するのが GSLB です。専用装置が不要な手軽さはむしろ利点で、登録するレコード数に2台までという制限はなく、利用者が使うドメイン名は1つのまま変わりません。

</details>

**問2.** GSLB（広域負荷分散）の説明として、適切なものはどれでしょう？

1. 1台のサーバ内で CPU の負荷を複数のコアに分散する仕組みである
2. すべてのサイトの IP アドレスを常に固定の順序で返す仕組みである
3. 各サイトへのヘルスチェックの結果に基づき、正常なサイトの IP アドレスだけを DNS 応答として返す仕組みである
4. 拠点間の通信を暗号化する仕組みである

<details><summary>答えと解説</summary>

正解: **3**

GSLB は DNS とヘルスチェックを組み合わせ、障害サイトの IP を応答から除外することで、利用者を名前解決の時点で正常なサイトへ誘導します。地理的に離れたサイト間の負荷分散や災害対策に使われます。CPU コアへの分散はサーバ内部の話で、固定順序で全 IP を返すだけでは DNS ラウンドロビンの弱点を解決できません。暗号化は VPN の役割です。

</details>

**問3.** GSLB で DNS 応答の TTL を短く設定する理由はどれでしょう？

1. サイト切り替え時に、利用者側のキャッシュ DNS に古い IP アドレスが残り続けて旧サイトへアクセスされるのを防ぐため
2. DNS サーバのディスク容量を節約するため
3. ゾーン転送を高速化するため
4. TTL が長いほど通信が暗号化されにくくなるため

<details><summary>答えと解説</summary>

正解: **1**

DNS の応答はキャッシュ DNS サーバに TTL の期間だけ保存されます。TTL が長いと、GSLB が応答を切り替えた後もキャッシュ上の旧 IP が使われ続け、利用者が障害サイトへ向かってしまいます。TTL を短くすれば切り替えが早く行き渡ります。TTL はキャッシュの保持時間であり、ディスク容量やゾーン転送の速度、暗号化の強度とは関係ありません。

</details>

**問4.** DR のバックアップサイトのうち「ホットサイト」の説明として、適切なものはどれでしょう？

1. 建物と電源などの設備枠だけを確保しておき、被災後に機器を搬入するサイト
2. 機器は設置済みだが普段は停止しており、被災後に起動と設定を行うサイト
3. 本番サイトと同じ建物内に置いた予備ラックのこと
4. 本番と同等の設備を常時稼働させておき、被災時にほぼ即時に切り替えられるサイト

<details><summary>答えと解説</summary>

正解: **4**

ホットサイトは本番同等のシステムを常時稼働・データ同期させておく方式で、復旧が最も速い代わりにコストが最も高くなります。設備枠だけを確保するのはコールドサイト、機器はあるが被災後に立ち上げるのはウォームサイトの説明です。同じ建物内の予備ラックでは建物ごと被災する災害に対応できず、サイト冗長とは言えません。

</details>
