# 第14章 TCPとUDP

トランスポート層の主役、TCP と UDP の章です。コネクションの確立から、ウィンドウ制御・再送・輻輳制御、そして TIME_WAIT や MTU/MSS が絡むトラブルまで、午後試験の計算・記述問題に直結する内容を学びます。

## 1. TCP と UDP の違い・ポート番号

IP はパケットを「宛先のホストまで」届けますが、そのホストの**どのアプリケーション**に渡すかまでは面倒を見ません。そこを担うのがトランスポート層の **TCP** と **UDP** で、アプリケーションは**ポート番号**で識別されます。

### TCP と UDP の比較

| 観点 | TCP | UDP |
|---|---|---|
| 事前のコネクション | 確立する | しない |
| 信頼性 | 順序制御・再送あり | なし（届いたら儲けもの） |
| 制御の重さ | 重い（ヘッダ20バイト〜） | 軽い（ヘッダ8バイト） |
| 主な用途 | Web・メール・ファイル転送 | DNS・DHCP・音声/映像・NTP・SNMP |

音声通話（VoIP）で UDP を使うのは、**再送して遅れて届いた音声には価値がない**からです。信頼性より即時性を取る、という割り切りです。

### ポート番号と通信の識別

0〜1023 は**ウェルノウンポート**（HTTP=80、HTTPS=443、DNS=53、SMTP=25 など）としてサーバ側が使い、クライアント側は空いている番号（エフェメラルポート）を一時的に使います。1本の通信は**「送信元 IP・送信元ポート・宛先 IP・宛先ポート」の組**で識別されるため、1台の PC から同じ Web サーバへ複数の通信を同時に張っても混ざりません。

> 💡 コツ：🔴 代表的なウェルノウンポートと「通信は IP とポートの4つ組で識別される」という事実は、この後の NAPT やファイアウォールの理解の土台になります。

### 確認問題

**問1.** 音声通話（VoIP）の音声データの転送に TCP ではなく UDP が使われる主な理由はどれでしょう？

1. UDP のほうが暗号化が強力だから
2. 再送で遅れて届いた音声データには価値がなく、再送や順序制御より即時性が重要だから
3. TCP は音声データを転送できない仕様だから
4. UDP はパケットを絶対に損失しないから

<details><summary>答えと解説</summary>

正解: **2**

音声はリアルタイム性が命であり、再送を待つくらいなら多少の欠落を許容して流し続けるほうが品質が保てるため、制御の軽い UDP が使われます。TCP でも音声データ自体は運べますが遅延が増えます。UDP に強力な暗号化機能はなく（暗号化は別の層で行います）、損失しない保証もありません。

</details>

**問2.** 1台の PC が同じ Web サーバに対して複数の TCP コネクションを同時に張っても、サーバが応答を取り違えないのはなぜでしょう？

1. コネクションは1台につき1本しか張れないから
2. サーバが応答を全クライアントにブロードキャストするから
3. MAC アドレスでコネクションを識別しているから
4. 送信元 IP・送信元ポート・宛先 IP・宛先ポートの組がコネクションごとに異なるから

<details><summary>答えと解説</summary>

正解: **4**

通信は IP アドレスとポート番号の4つ組で識別され、PC はコネクションごとに別の送信元ポート（エフェメラルポート）を使うため、宛先が同じでも組合せが一意になり区別できます。コネクション数に1本という制限はなく、応答は該当の相手にだけ返されます。MAC アドレスは L2 の転送に使うもので、コネクションの識別には使いません。

</details>

**問3.** DNS の名前解決で標準的に使われるウェルノウンポート番号はどれでしょう？

1. 53
2. 80
3. 443
4. 25

<details><summary>答えと解説</summary>

正解: **1**

DNS はポート 53 を使い、通常の問い合わせは UDP で行われます（応答が大きい場合などは TCP も使用）。80 は HTTP、443 は HTTPS、25 は SMTP（メール転送）のウェルノウンポートです。主要プロトコルとポート番号の対応は午前Ⅱの定番知識です。

</details>

**問4.** TCP にはあって UDP にはない機能はどれでしょう？

1. ポート番号によるアプリケーションの識別
2. IP アドレスによる宛先ホストの指定
3. シーケンス番号と確認応答による順序制御・再送（信頼性の保証）
4. チェックサムによる誤り検出

<details><summary>答えと解説</summary>

正解: **3**

TCP はシーケンス番号と ACK でデータの到達を確認し、抜けがあれば再送し、順序も並べ直します。UDP にはこの信頼性の仕組みがありません。一方、ポート番号とチェックサムは UDP のヘッダにも存在する共通機能で、宛先 IP アドレスの指定はそもそも下位の IP 層の仕事です。

</details>

## 2. 3ウェイハンドシェイクとコネクション終了

TCP はデータを送る前に、**3ウェイハンドシェイク**でコネクションを確立します。PC（クライアント）が Web サーバに接続する流れを追ってみましょう。

### 確立：3つのセグメントの往復

1. **PC → サーバ：SYN**（シーケンス番号 x を提示。「接続したい」）
2. **サーバ → PC：SYN/ACK**（自分のシーケンス番号 y を提示しつつ、確認応答番号 **x+1** で「x まで受け取った、次は x+1 をくれ」）
3. **PC → サーバ：ACK**（確認応答番号 **y+1**。「そちらの y も受け取った」）

ここで交換した初期シーケンス番号を起点に、以後のデータの順序管理と再送が行われます。2回のやり取りでは「PC→サーバ」「サーバ→PC」**両方向が通ることと互いの初期番号**を双方が確認しきれないため、3回必要なのです。

### 終了：FIN の交換

終了は「もう送るものがない」ことを **FIN** で伝え合います。

1. PC → サーバ：**FIN** → サーバ → PC：**ACK**
2. サーバ → PC：**FIN** → PC → サーバ：**ACK**

片方が FIN を送った後も、相手からの受信は続けられます（**ハーフクローズ**）。たとえば PC が送信を終えても、サーバからの残りの応答を受け取り切ってから完全に閉じられます。

> 💡 コツ：🔴「確認応答番号 = 次に受け取りたいシーケンス番号」という読み方を体に入れると、午後のパケット図（シーケンス番号の穴埋め）が得点源になります。

### 確認問題

**問1.** TCP の3ウェイハンドシェイクで交換されるセグメントの正しい順序はどれでしょう？

1. ACK → SYN → SYN/ACK
2. SYN → ACK → SYN/ACK
3. SYN → SYN/ACK → ACK
4. FIN → FIN/ACK → ACK

<details><summary>答えと解説</summary>

正解: **3**

クライアントが SYN で接続を要求し、サーバが SYN/ACK で応答と自分側の接続要求を返し、最後にクライアントの ACK で確立完了、という3段階です。SYN より先に ACK が送られることはなく、FIN はコネクション終了時に使うフラグです。

</details>

**問2.** クライアントがシーケンス番号 x の SYN を送ったとき、サーバが返す SYN/ACK の確認応答番号は x+1 です。この値が意味するものはどれでしょう？

1. 「次に受け取りたいのはシーケンス番号 x+1 からのデータである」という通知
2. サーバがこれから送るデータの総バイト数
3. コネクションに割り当てられたポート番号
4. 再送までの待ち時間（ミリ秒）

<details><summary>答えと解説</summary>

正解: **1**

TCP の確認応答番号は「ここまで受け取ったので、次はこの番号をください」という意味で、x を受け取ったから次は x+1、と読みます。この読み方はデータ転送中の ACK でも同じで、午後のシーケンス番号穴埋め問題の基本です。送信予定のバイト数・ポート番号・再送タイマの値を表すフィールドではありません。

</details>

**問3.** コネクション確立のやり取りが2回ではなく3回必要なのはなぜでしょう？

1. 3回繰り返すことで伝送誤りを多数決で訂正するため
2. 双方が「自分の送った SYN が相手に届いたこと」を確認し、両方向の到達性と互いの初期シーケンス番号を確定させるため
3. 途中のルータが3台以上あることを確認するため
4. 暗号鍵を3分割して安全に交換するため

<details><summary>答えと解説</summary>

正解: **2**

2回目（SYN/ACK）でクライアントは自分の SYN が届いたと分かりますが、サーバはまだ自分の SYN/ACK が届いたか分かりません。3回目の ACK で初めてサーバ側も確認でき、双方向の到達性と初期シーケンス番号の合意が完成します。多数決による誤り訂正や経由ルータ数の確認、鍵交換は3ウェイハンドシェイクの目的ではありません。

</details>

**問4.** TCP のコネクション終了（正常終了）について、正しい説明はどれでしょう？

1. どちらか一方が FIN を送った瞬間に、両方向の通信が同時に切断される
2. RST セグメントを交換して合意のうえで切断する
3. 3ウェイハンドシェイクをもう一度行って切断する
4. 双方がそれぞれ FIN を送って ACK を受け、片方が FIN を送った後も相手からの受信は継続できる

<details><summary>答えと解説</summary>

正解: **4**

正常終了では各方向を FIN と ACK で個別に閉じるため、自分の送信を終えても相手の残りデータは受信し続けられます（ハーフクローズ）。一方の FIN で両方向が同時に切れるわけではありません。RST は異常時などの即時切断に使うもので合意手順ではなく、3ウェイハンドシェイクは確立側の手順です。

</details>

## 3. ウィンドウ制御・再送制御・輻輳制御

1セグメント送るたびに ACK を待っていては、遠距離の通信ほど待ち時間だらけになります。TCP は**ウィンドウ制御**でこれを解決します。

### ウィンドウ制御（フロー制御）

**ウィンドウサイズ = ACK を待たずに連続して送ってよいデータ量**です。受信側は自分のバッファの空きをウィンドウサイズとして通知し、送信側はその範囲内でまとめて送ります。ACK が返るたびに送れる範囲が前へずれていく様子から**スライディングウィンドウ**と呼ばれます。このときスループットの上限は、およそ**ウィンドウサイズ ÷ RTT（往復遅延時間）**で決まります。たとえばウィンドウ 64k バイト（= 512k ビット）、RTT 0.1 秒なら最大約 5.1M ビット/秒です。回線がどんなに太くても、RTT が大きいとこの式が頭打ちの原因になります。

### 再送制御

送信側は ACK が**タイムアウト**まで返らなければ再送します。さらに、同じ確認応答番号の**重複 ACK を3回**受け取ると「そのセグメントだけ抜けた」と判断し、タイムアウトを待たずに再送します（**高速再転送**）。

### 輻輳制御

受信側の都合（フロー制御）とは別に、**ネットワークの混雑（輻輳）**を悪化させないよう、送信側は**スロースタート**で小さく送り始め、ACK が返るたびに送信量を増やし、パケットロスを検知したら送信量を絞ります。

> 💡 コツ：🔴「スループット ≒ ウィンドウ ÷ RTT」は午後の計算問題の超頻出公式です。単位（バイトとビット）の換算を忘れずに。

### 確認問題

**問1.** TCP のウィンドウ制御の目的として、最も適切なものはどれでしょう？

1. セグメントを暗号化して盗聴を防ぐこと
2. ACK を待たずに複数のセグメントを連続送信し、受信側の処理能力の範囲で転送効率を高めること
3. 1セグメントごとに必ず ACK を待つことで信頼性を高めること
4. IP アドレスの変換テーブルを管理すること

<details><summary>答えと解説</summary>

正解: **2**

ウィンドウサイズは「ACK を待たずに送ってよい量」で、受信側のバッファの空きに応じて調整されるため、待ち時間を減らしつつ受信側があふれるのも防げます。1つずつ ACK を待つ方式はまさにウィンドウ制御が解決したい非効率な状態です。暗号化やアドレス変換はウィンドウ制御の機能ではありません。

</details>

**問2.** ウィンドウサイズ 64k バイト（512k ビット）、RTT 100 ミリ秒の TCP コネクションで期待できるスループットの上限はおよそどれでしょう？

1. 約 0.5M ビット/秒
2. 約 51.2M ビット/秒
3. 約 5.1M ビット/秒
4. 約 512M ビット/秒

<details><summary>答えと解説</summary>

正解: **3**

スループットの上限はウィンドウサイズ ÷ RTT で、512k ビット ÷ 0.1 秒 = 約 5.1M ビット/秒です。この問題ではバイトをビットに換算（×8）する点と、100 ミリ秒 = 0.1 秒の単位換算がポイントで、換算を誤ると他の選択肢のような桁違いの値になります。回線帯域がこれより太くても、ウィンドウと RTT がボトルネックになります。

</details>

**問3.** 送信側が同じ確認応答番号の重複 ACK を3回受け取ったときの動作はどれでしょう？

1. タイムアウトを待たずに、抜けたセグメントを直ちに再送する（高速再転送）
2. コネクションを直ちに切断する
3. 受信側に全データの最初からの再送を要求する
4. ウィンドウサイズをゼロにして送信を停止する

<details><summary>答えと解説</summary>

正解: **1**

重複 ACK が続くのは「後続は届いているのに特定のセグメントだけ抜けている」サインなので、タイムアウトを待たずにそのセグメントを再送します（高速再転送）。これはロスからの回復を速める仕組みであり、切断やゼロウィンドウによる停止は行いません。再送するのは抜けた部分だけで、最初からやり直すわけでもありません。

</details>

**問4.** TCP のフロー制御と輻輳制御の違いの説明として、正しいものはどれでしょう？

1. フロー制御は送信側の CPU 負荷、輻輳制御は受信側の CPU 負荷を抑える仕組みである
2. 両者は同じ仕組みの別名である
3. フロー制御は UDP 専用、輻輳制御は TCP 専用の仕組みである
4. フロー制御は受信側の処理能力（バッファ）あふれを防ぎ、輻輳制御はネットワーク自体の混雑の悪化を防ぐ

<details><summary>答えと解説</summary>

正解: **4**

フロー制御は受信側が通知するウィンドウで「相手をあふれさせない」仕組み、輻輳制御はスロースタートなどで「ネットワークを詰まらせない」仕組みで、守る対象が違います。送信側は両方の制約の小さいほうに従って送信量を決めます。両者は別の仕組みであり、CPU 負荷の制御でもなく、UDP にはそもそもどちらの仕組みもありません。

</details>

## 4. TCP の状態とトラブル（TIME_WAIT・RST・MTU/MSS）

TCP の実務トラブルで名前がよく挙がる3つのキーワードを押さえましょう。

### TIME_WAIT

コネクションを先に閉じた側（最後の ACK を送った側）は、すぐには消えず **TIME_WAIT 状態でしばらく待機**します。目的は、(1) 最後の ACK が失われたとき相手の FIN 再送に応答するため、(2) ネットワーク上を遅れて漂っている古いセグメントが、同じ IP・ポートの組を再利用した**新しいコネクションに紛れ込むのを防ぐ**ためです。短時間に大量の接続と切断を繰り返すと TIME_WAIT が溜まり、ポートを使い切ることがあります。

### RST

**RST（リセット）**は「このコネクションは存在しない/継続できない」ことを示す即時切断の通知です。たとえば**閉じているポートに SYN を送ると RST が返り**、接続は拒否されます。応答すらない（無視される）場合はファイアウォールでの破棄が疑われる、という切り分けにも使えます。

### MTU と MSS

**MTU** は1回に運べる IP パケットの最大長（イーサネットは 1500 バイト）、**MSS** は TCP のデータ部分の最大長で、**MTU − IP ヘッダ 20 − TCP ヘッダ 20 = 1460 バイト**が基本です。MSS は3ウェイハンドシェイク時に互いに通知し、**小さいほうに合わせます**。VPN などのトンネルを挟むとヘッダが増えて実質 MTU が縮むため、「小さい通信は通るのに大きなファイル転送だけ失敗する」という典型トラブルが起きます。

> 💡 コツ：🟡 1500/20/20/1460 の数字の関係は午前Ⅱ・午後の両方で頻出です。

### 確認問題

**問1.** MTU が 1500 バイトのイーサネット環境で、TCP の MSS の基本値はいくつでしょう（IP・TCP ヘッダはともに 20 バイトとする）？

1. 1500 バイト
2. 1460 バイト
3. 1480 バイト
4. 1540 バイト

<details><summary>答えと解説</summary>

正解: **2**

MSS は TCP のデータ部分の最大長なので、MTU 1500 から IP ヘッダ 20 バイトと TCP ヘッダ 20 バイトを引いた 1460 バイトです。1500 は MTU そのもの、1480 は IP ヘッダだけを引いた値（TCP ヘッダの引き忘れ）、1540 は逆に足してしまった値で、いずれも誤りです。

</details>

**問2.** コネクションを先に閉じた側が TIME_WAIT 状態で待機する目的として、正しいものはどれでしょう？

1. 次のコネクションのためにウィンドウサイズを再計算するため
2. 相手にデータの再送を要求するため
3. サーバの負荷が下がるのを待つため
4. 最後の ACK の喪失に備えるとともに、遅延して届く古いセグメントが同じポートの組を使う新しいコネクションに紛れ込むのを防ぐため

<details><summary>答えと解説</summary>

正解: **4**

TIME_WAIT は、最後の ACK が失われた場合の相手の FIN 再送への応答と、ネットワークに残った古いセグメントの新コネクションへの混入防止のための待機時間です。この間は同じ IP・ポートの組を再利用できないため、大量の短い接続を繰り返すとポート枯渇の原因になります。ウィンドウ再計算・再送要求・負荷調整のための状態ではありません。

</details>

**問3.** サーバの閉じている（どのアプリケーションも待ち受けていない）TCP ポートに SYN を送った場合、標準的な応答はどれでしょう？

1. RST が返り、接続が拒否される
2. SYN/ACK が返り、接続がいったん確立される
3. FIN が返り、正常終了の手順が始まる
4. ICMP エコー応答が返る

<details><summary>答えと解説</summary>

正解: **1**

待ち受けのないポートへの SYN には RST が返り、クライアントは即座に接続失敗を知ります。応答が何もない場合はファイアウォールによる破棄が疑われる、という切り分けにも使える知識です。SYN/ACK は待ち受け中のポート、FIN は確立済みコネクションの終了に使うもので、ICMP エコー応答は ping に対する返答です。

</details>

**問4.** 拠点間を VPN で接続したところ「ping や小さな通信は成功するのに、大きなファイル転送だけが途中で止まる」という障害が起きました。最も疑うべき原因はどれでしょう？

1. DNS サーバの名前解決の失敗
2. VRRP のマスタ切替の失敗
3. トンネルのヘッダ分だけ実質 MTU が小さくなり、サイズの大きいパケットが通過できなくなっている（MTU/MSS の問題）
4. ウェルノウンポートの番号の重複

<details><summary>答えと解説</summary>

正解: **3**

VPN はパケットに追加ヘッダを付けるため経路の実質 MTU が縮み、小さいパケットは通るのに MTU を超える大きいパケットだけが破棄される、という症状が典型的に起きます。対策は MSS の調整などです。名前解決の失敗なら接続自体ができず、VRRP の問題なら通信全体が止まるはずで、サイズ依存の症状とは合いません。ポート番号の重複はこの症状の原因になりません。

</details>
