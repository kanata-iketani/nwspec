# 第5章 データベースのきほん

午前Ⅰの定番分野であるデータベースを基礎から学ぶ章です。表のしくみ・SQL・正規化・トランザクションという「毎回どれかは出る」範囲を、計算なしで得点源にします。

## 1. 関係データベースと主キー・外部キー

**関係データベース（RDB）**は、データを**表（テーブル）**の形で管理するしくみです。見た目は表計算ソフトの表に似ていますが、「どの行のことか」を厳密に特定できるようにルールが決められています。

### 表の用語

| 用語 | 意味 |
|---|---|
| 行（レコード） | 1件分のデータ（例：社員1人） |
| 列（カラム） | 項目（例：氏名、部署コード） |
| 主キー | 行を一意に特定する列（または列の組） |
| 外部キー | 他の表の主キーを参照する列 |

### 主キーのルール

主キーは「社員番号」のように**値の重複が許されず、空（NULL）も許されません**。1つの列だけで行を特定できないときは、複数の列を組み合わせた**複合キー**を主キーにします。

### 外部キーと参照整合性

社員表の「部署コード」列が部署表の主キーを参照する——これが外部キーです。参照先の部署表に存在しない部署コードは社員表に登録できません。この「宙に浮いた参照を許さない」性質を**参照整合性**と呼びます。

> 💡 コツ：主キー＝「その表の中で行を特定する背番号」、外部キー＝「他の表への橋渡し」とイメージすると混同しません。

🔴 午前Ⅰの頻出です。「主キーは重複・NULL 禁止」「外部キーは参照整合性を保つ」の2点をまず確実に覚えましょう。

### 確認問題

**問1.** 関係データベースの主キーの説明として、最も適切なものはどれでしょう？

1. 他の表のデータを参照するために使う列である
2. 表の中の行を一意に識別する列（または列の組）で、値の重複も NULL も許されない
3. 検索を高速化するためだけに付ける列で、値は自由に重複してよい
4. 表の先頭の列のことで、必ず数値でなければならない

<details><summary>答えと解説</summary>

正解: **2**

主キーは行を一意に特定するための列（または列の組）で、重複も NULL も許されません。「他の表を参照する列」は外部キーの説明です。検索の高速化はインデックスの役割で、主キーの本質ではありません。主キーは先頭の列である必要も、数値である必要もありません。

</details>

**問2.** 外部キーの役割として、最も適切なものはどれでしょう？

1. 表の中の行を並べ替える順序を決める
2. 行を一意に識別し、NULL を禁止する
3. 表の列数の上限を定義する
4. 他の表の主キーを参照し、表と表の間のつながりと整合性を保つ

<details><summary>答えと解説</summary>

正解: **4**

外部キーは「社員表の部署コードが部署表の主キーを参照する」のように、表どうしを関連付け、存在しない値の参照を防ぎます（参照整合性）。行の一意識別と NULL 禁止は主キーの役割です。並べ替えは SQL の ORDER BY で指定するもので、列数の上限を決める機能はキーにはありません。

</details>

**問3.** 複合キーの説明として、適切なものはどれでしょう？

1. 1つの列だけでは行を特定できないとき、複数の列を組み合わせて主キーとしたもの
2. 複数の表にまたがって同じ名前を付けた列のこと
3. 主キーと外部キーを同じ列に設定したもの
4. NULL を許す特別な主キーのこと

<details><summary>答えと解説</summary>

正解: **1**

例えば「受注番号＋商品番号」のように、単独では行を特定できない列を組み合わせて主キーにしたものが複合キーです。複数の表で同じ列名を使うこと自体は複合キーとは無関係です。1つの列が主キーかつ外部キーになることはあり得ますが、それは複合キーの定義ではありません。主キーは複合キーであっても NULL は許されません。

</details>

**問4.** 部署表（主キー：部署コード）を参照する外部キーを社員表の「部署コード」列に設定しました。参照整合性が保たれているとき、起こり得ないのはどれでしょう？

1. 社員が1人もいない部署が部署表に存在する
2. 同じ部署コードを持つ社員が複数いる
3. 部署表に存在しない部署コードを持つ社員の行が登録される
4. 社員表に新しい行を追加する

<details><summary>答えと解説</summary>

正解: **3**

参照整合性とは「外部キーの値は参照先の主キーに必ず存在しなければならない」というルールなので、部署表にない部署コードを持つ社員は登録できません。社員がいない部署は参照されていないだけで問題ありません。外部キーの値は重複してよいので、同じ部署の社員が複数いるのは普通のことです。整合性を満たす行の追加はもちろん可能です。

</details>

## 2. SQL のきほん（SELECT・WHERE・結合・集計）

**SQL** は、関係データベースからデータを取り出したり更新したりするための言語です。午前Ⅰでは「読めれば解ける」レベルで十分なので、基本の形を押さえましょう。

### 基本の形

```sql
SELECT 氏名, 給与 FROM 社員
WHERE 部署コード = 'D01'
ORDER BY 給与 DESC
```

SELECT が「どの列を」、FROM が「どの表から」、WHERE が「どの行を」、ORDER BY が「どう並べるか」を指定します。

### 集計とグループ化

| 書き方 | 意味 |
|---|---|
| COUNT(*)・SUM・AVG・MAX・MIN | 行数・合計・平均・最大・最小 |
| GROUP BY 部署コード | 部署ごとにまとめて集計 |
| HAVING AVG(給与) >= 300000 | 集計した**結果**をさらに絞る |

**WHERE はグループ化の前に行を絞り、HAVING はグループ化の後に集計結果を絞る**——ここが最頻出の引っかけです。

### 結合（JOIN）

2つの表を「部署コードが等しい行どうし」のようにつなげるのが結合です。**内部結合**では、両方の表で条件に一致した行だけが結果に残ります。

> 💡 コツ：SQL は英語の語順で読むと意味が取れます。「選べ（SELECT）〜から（FROM）〜という条件で（WHERE）」。

🔴 WHERE と HAVING の違い、内部結合の結果がどうなるかは、そのまま出題されます。確実に区別できるようにしましょう。

### 確認問題

**問1.** 「部署ごとの平均給与を求め、平均給与が30万円以上の部署だけを表示したい」とき、SQL で使う組み合わせとして適切なものはどれでしょう？

1. ORDER BY と WHERE
2. DISTINCT と ORDER BY
3. GROUP BY と HAVING
4. WHERE だけで実現できる

<details><summary>答えと解説</summary>

正解: **3**

部署ごとの集計には GROUP BY、集計した平均値による絞り込みには HAVING を使います。WHERE はグループ化の前に個々の行を絞る句なので、「平均給与」という集計結果の条件には使えません。ORDER BY は並べ替え、DISTINCT は重複行の除去で、どちらも集計条件の指定はできません。

</details>

**問2.** WHERE 句と HAVING 句の違いの説明として、適切なものはどれでしょう？

1. WHERE はグループ化の前に行を絞り込み、HAVING はグループ化の後に集計結果を絞り込む
2. WHERE は数値専用、HAVING は文字列専用の条件句である
3. WHERE と HAVING は書く位置が違うだけで、働きはまったく同じである
4. HAVING はグループ化の前に行を絞り込み、WHERE は集計結果を絞り込む

<details><summary>答えと解説</summary>

正解: **1**

WHERE は個々の行に対する条件（グループ化の前）、HAVING は GROUP BY でまとめた後の集計結果に対する条件です。選択肢の最後はこの関係が逆になっています。データ型による使い分けという決まりはなく、働きが同じというのも誤りです。

</details>

**問3.** 社員表と部署表を部署コードで内部結合したとき、結果に含まれる行はどれでしょう？

1. 社員表のすべての行（部署コードが一致しなくても含まれる）
2. 両方の表のすべての行を単純に足し合わせたもの
3. 部署表のすべての行（社員がいない部署も含まれる）
4. 両方の表で部署コードが一致した行だけ

<details><summary>答えと解説</summary>

正解: **4**

内部結合は、結合条件（ここでは部署コードの一致）を満たす行どうしだけを結果に残します。一致しない行も残したい場合は外部結合を使います。「片方の表の全行を残す」のは外部結合の動き、「全行を足し合わせる」のは結合ではなく UNION に近いイメージで、どちらも内部結合の説明としては誤りです。

</details>

**問4.** SELECT COUNT(*) FROM 社員 WHERE 部署コード = 'D01' が返すものはどれでしょう？

1. 社員表の列の数
2. 部署コードが D01 の社員の行数（人数）
3. 部署コードが D01 の社員の給与の合計
4. 社員表のすべての行数

<details><summary>答えと解説</summary>

正解: **2**

COUNT(*) は条件に合った行の数を数える集計関数で、WHERE で D01 に絞っているので「D01 に所属する社員の人数」が返ります。合計を求めるのは SUM です。WHERE で絞り込んでいるため全行数にはならず、列の数を数える機能は COUNT(*) にはありません。

</details>

## 3. 正規化（第1〜第3正規形）

**正規化**とは、表の設計を整理して**データの重複をなくし、更新時の矛盾（更新時異常）を防ぐ**手順です。同じ情報が何か所にも書かれていると、1か所だけ直し忘れて食い違いが起きます。それを構造的に防ぐのが目的です。

### 3つのステップ

| 正規形 | やること |
|---|---|
| 第1正規形 | 繰り返し項目をなくし、1マスに1つの値だけにする |
| 第2正規形 | **複合主キーの一部**だけに従属する列を別の表に分ける（部分関数従属の排除） |
| 第3正規形 | **主キー以外の列**に従属する列を別の表に分ける（推移的関数従属の排除） |

### 具体例

受注表（受注番号＋商品番号が主キー）に「商品名」があると、商品名は主キーの一部（商品番号）だけで決まるので第2正規形違反です。商品表に分けます。さらに社員表に「部署コード」と「部署名」があると、部署名は主キー（社員番号）ではなく部署コードで決まるので第3正規形違反です。部署表に分けます。

> 💡 コツ：「列が何で決まるか」を追いかけます。キー全体で決まる＝OK、キーの一部で決まる＝第2違反、キー以外で決まる＝第3違反。

🔴 午前Ⅰでは「この表は第何正規形か」「第2正規化で何を分けるか」が定番です。上の表の2行目・3行目を言えるようにしましょう。

### 確認問題

**問1.** データベースを正規化する主な目的はどれでしょう？

1. 検索処理をどんな場合でも必ず高速化するため
2. データの重複をなくし、更新時に矛盾が生じるのを防ぐため
3. 表の数を減らしてデータベースを小さく見せるため
4. SQL を使わずにデータを操作できるようにするため

<details><summary>答えと解説</summary>

正解: **2**

正規化の目的は、同じ情報の重複をなくして更新時異常（直し忘れによる食い違いなど）を防ぐことです。正規化すると表が分かれて結合が増えるため、検索はむしろ遅くなる場合もあります。表の数は正規化で増えるのが普通です。SQL が不要になることもありません。

</details>

**問2.** 第1正規形にするために行う作業はどれでしょう？

1. 主キー以外の列に従属する列を別の表に分ける
2. すべての列に NULL を許可する
3. 複合主キーの一部に従属する列を別の表に分ける
4. 1つのマスに複数の値が入っている繰り返し項目をなくし、1マス1値にする

<details><summary>答えと解説</summary>

正解: **4**

第1正規形は「1つのマスには1つの値だけ」という状態にすることで、例えば1行に商品が3つ並ぶような繰り返しを行に分解します。複合主キーの一部への従属（部分関数従属）の排除は第2正規形、主キー以外への従属（推移的関数従属）の排除は第3正規形の作業です。NULL の許可は正規化とは関係ありません。

</details>

**問3.** 受注明細表の主キーが「受注番号＋商品番号」の複合キーで、この表に「商品名」列があります。商品名は商品番号だけで決まるとき、この状況の説明として適切なものはどれでしょう？

1. 部分関数従属があるため第2正規形を満たしておらず、商品表に分離すべきである
2. 推移的関数従属があるため第3正規形を満たしていない
3. 繰り返し項目があるため第1正規形を満たしていない
4. 正規化上の問題はなく、このままでよい

<details><summary>答えと解説</summary>

正解: **1**

商品名が複合主キーの一部（商品番号）だけで決まる状態を部分関数従属といい、第2正規形違反です。商品番号と商品名を商品表に分離します。推移的関数従属は「主キー以外の列で決まる」場合なので当てはまりません。1マスに複数の値が入っているわけではないので第1正規形は満たしています。重複した商品名を何行にも持つことになるため「問題なし」も誤りです。

</details>

**問4.** 社員表（主キー：社員番号）に「部署コード」と「部署名」の列があります。部署名は部署コードで決まります。第3正規形にするための対応はどれでしょう？

1. 部署名を主キーに追加して複合キーにする
2. 社員番号の列を削除する
3. 部署コードと部署名を部署表として分離し、社員表には部署コードだけを残す
4. 部署名の列に NULL を設定して空にしておく

<details><summary>答えと解説</summary>

正解: **3**

部署名が主キー（社員番号）ではなく部署コードに従属している状態が推移的関数従属で、第3正規形にするには部署表（部署コード・部署名）を分離します。部署名を主キーに加えても従属関係は解消されません。社員番号は行を識別する主キーなので削除できません。NULL にするのはデータを消すだけで設計の問題は解決しません。

</details>

## 4. トランザクション（ACID・排他制御・コミットとロールバック）

**トランザクション**とは、「A さんの口座から1万円引く」「B さんの口座に1万円足す」のように、**まとめて成功しなければ意味がない一連の処理を1つの単位**として扱うしくみです。途中で止まると「引かれたのに足されていない」事故になります。

### ACID 特性

| 特性 | 意味 |
|---|---|
| 原子性（Atomicity） | 全部実行されるか、まったく実行されないかのどちらか |
| 一貫性（Consistency） | 処理の前後でデータの整合性が保たれる |
| 独立性（Isolation） | 同時に動く他のトランザクションの影響を受けない |
| 耐久性（Durability） | 完了した結果は障害が起きても失われない |

### コミットとロールバック

処理がすべて成功したら**コミット**（確定）、途中で失敗したら**ロールバック**（開始前の状態に巻き戻し）します。

### 排他制御とデッドロック

複数の利用者が同じデータを同時に更新すると矛盾が起きるため、**ロック**をかけて順番に処理させるのが排他制御です。ただし、2つのトランザクションが互いに相手のロック解放を待ち合って動けなくなる**デッドロック**に注意が必要です。

> 💡 コツ：ACID は「銀行振込が途中で止まったら？」を想像すると4つとも腹落ちします。

🟡 ACID の4つの名前と意味、コミット／ロールバックの違いを押さえれば十分です。

### 確認問題

**問1.** トランザクションの原子性（Atomicity）の説明として、適切なものはどれでしょう？

1. 一連の処理がすべて実行されるか、まったく実行されないかのどちらかになる性質
2. 完了した処理の結果が障害後も失われない性質
3. 同時に実行される他の処理の影響を受けない性質
4. 処理の前後でデータの整合性が保たれる性質

<details><summary>答えと解説</summary>

正解: **1**

原子性は「中途半端な状態を残さない」性質で、振込の途中で障害が起きても「引き落としだけ実行済み」にはなりません。障害後も結果が残るのは耐久性（Durability）、他の処理の影響を受けないのは独立性（Isolation）、整合性が保たれるのは一貫性（Consistency）の説明です。

</details>

**問2.** ロールバックの説明として、適切なものはどれでしょう？

1. トランザクションの処理結果を確定してデータベースに反映すること
2. データベース全体のバックアップを取得すること
3. 障害や失敗が起きたとき、トランザクション開始前の状態に巻き戻すこと
4. 複数の表を1つにまとめて管理すること

<details><summary>答えと解説</summary>

正解: **3**

ロールバックは、途中まで行った変更を取り消してトランザクション開始前の状態に戻す操作です。結果を確定するのは逆の操作であるコミットです。バックアップの取得は障害対策の別の作業で、表をまとめるのは正規化やテーブル設計の話であり、どちらもロールバックとは異なります。

</details>

**問3.** データベースで排他制御（ロック）を行う主な目的はどれでしょう？

1. データベースの使用容量を減らすため
2. 複数の利用者が同じデータを同時に更新して矛盾が生じるのを防ぐため
3. SQL の文法エラーを自動的に修正するため
4. 問い合わせの応答時間を必ず短くするため

<details><summary>答えと解説</summary>

正解: **2**

排他制御は、同じデータへの同時更新による矛盾（更新の消失など）を防ぐために、処理中のデータをロックして他の処理を待たせるしくみです。ロックは待ち時間を生むため応答時間はむしろ延びることがあります。容量の削減や文法エラーの修正はロックの機能ではありません。

</details>

**問4.** デッドロックの説明として、適切なものはどれでしょう？

1. ロックの取得に成功して処理が高速化された状態
2. データベースの管理者がすべての利用者のアクセスを禁止した状態
3. ディスクが満杯になってデータを書き込めない状態
4. 2つのトランザクションが互いに相手のロック解放を待ち合い、どちらも進めなくなった状態

<details><summary>答えと解説</summary>

正解: **4**

デッドロックは、例えばトランザクション1がデータ A をロックして B を待ち、トランザクション2が B をロックして A を待つ、というすれ違いで両方が永久に止まる状態です。解消には一方を強制的にロールバックします。ロック成功による高速化や管理者によるアクセス禁止、ディスク満杯はいずれもデッドロックとは別の事象です。

</details>
