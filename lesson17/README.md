# 第17章 HTTP・メール・プロキシ

Web ページが表示されるまで、メールが届くまでの通信の流れを言葉で追える章です。HTTP・HTTPS(TLS)・メールの認証技術(SPF/DKIM/DMARC)・プロキシと CDN を扱います。

## 1. HTTP のきほん（メソッドとステータスコード）

ブラウザで Web ページを開く操作は、**HTTP** というプロトコルで「この URL のデータをください」とサーバに頼み、返事をもらうやり取りです。レストランの注文（リクエスト）と料理の提供（レスポンス）に例えられます。

### 主なメソッド（注文の種類）

| メソッド | 意味 |
|---|---|
| GET | データを取得する |
| POST | データを送信する（フォーム送信など） |
| PUT | データを置き換える |
| DELETE | データを削除する |

### ステータスコード（返事の種類）

| コード | 意味 |
|---|---|
| 200 | 成功（OK） |
| 301/302 | リダイレクト（別の場所へ案内） |
| 403 | 禁止（権限がない） |
| 404 | 見つからない |
| 500 | サーバ内部エラー |
| 503 | サービス利用不可（過負荷・メンテナンス） |

**先頭の数字**が分類で、4xx は「クライアント側の問題」、5xx は「サーバ側の問題」です。

### バージョンの違いをざっくり

- **HTTP/1.1**: テキスト形式。1つの TCP コネクションでは基本的に1つずつ順番に処理
- **HTTP/2**: バイナリ形式。**1本の TCP コネクションで複数のリクエストを並行処理**（多重化）
- **HTTP/3**: TCP をやめて **UDP 上の QUIC** を使い、さらに高速化

🔴 メソッドとステータスコードの分類（4xx=クライアント、5xx=サーバ）、HTTP/2=多重化・HTTP/3=UDP(QUIC) は午前Ⅱの定番です。

### 確認問題

**問1.** HTTP ステータスコード 404 と 503 の説明の組み合わせとして、適切なものはどれでしょう？

1. 404=サーバ内部エラー、503=リダイレクト
2. 404=要求されたリソースが見つからない、503=サーバが一時的にサービスを提供できない
3. 404=認証が必要、503=リソースが見つからない
4. 404=成功、503=サーバ内部エラー

<details><summary>答えと解説</summary>

正解: **2**

404 Not Found は「要求された URL のリソースが存在しない」、503 Service Unavailable は「過負荷やメンテナンスで一時的に応答できない」です。サーバ内部エラーは 500、リダイレクトは 301/302、成功は 200 なので他の選択肢は誤りです。

</details>

**問2.** HTTP/2 が HTTP/1.1 に対して高速化を実現した主な仕組みはどれでしょう？

1. 1本の TCP コネクション上で複数のリクエストとレスポンスを並行して多重化する
2. UDP を使って再送処理を省略する
3. すべての通信を平文にして暗号化処理をなくす
4. リクエストごとに必ず新しい TCP コネクションを張り直す

<details><summary>答えと解説</summary>

正解: **1**

HTTP/2 の中心的な改善は、1本の TCP コネクション上でのストリーム多重化です。UDP(QUIC) を使うのは HTTP/3 の特徴です。暗号化をなくす仕様はなく、実際には TLS との併用が一般的です。コネクションを毎回張り直すのはむしろ HTTP/1.0 的な非効率な動作です。

</details>

**問3.** HTTP/3 のトランスポートに関する説明として、適切なものはどれでしょう？

1. TCP の上で動作し、3ウェイハンドシェイクを2回行う
2. ICMP を使って到達確認を行う
3. UDP 上で動作する QUIC を使い、コネクション確立を高速化している
4. 物理層を無線に限定したプロトコルである

<details><summary>答えと解説</summary>

正解: **3**

HTTP/3 は TCP ではなく UDP 上の QUIC を採用し、コネクション確立と暗号化のネゴシエーションをまとめて行うことで高速化しています。TCP ベースなのは HTTP/2 までです。ICMP は疎通確認などに使う別のプロトコルで、HTTP/3 が物理層を限定することもありません。

</details>

**問4.** Web フォームに入力した会員情報を新規登録のためにサーバへ送る場合、一般的に使われる HTTP メソッドはどれでしょう？

1. GET
2. DELETE
3. HEAD
4. POST

<details><summary>答えと解説</summary>

正解: **4**

フォームデータの送信には、リクエストボディにデータを載せられる POST を使うのが一般的です。GET は取得が目的で、データが URL に現れるため登録用途に不向きです。DELETE は削除、HEAD はヘッダ情報のみを取得するメソッドです。

</details>

## 2. HTTPS と TLS（ハンドシェイク・サーバ証明書・SNI）

HTTP は平文なので、途中の経路で盗み見（盗聴）や書き換えができてしまいます。そこで **TLS** で暗号化したものが **HTTPS** です。URL が `https://`、ポートは **443** になります。

### TLS ハンドシェイクの流れ（ざっくり）

1. **ClientHello**: クライアントが「使える暗号方式の一覧」と接続先ホスト名（SNI）を送る
2. **ServerHello + サーバ証明書**: サーバが暗号方式を選び、自分の証明書を提示する
3. **証明書の検証**: クライアントは証明書が信頼できる **CA（認証局）** に署名されているか、ドメイン名が一致するかを確認する
4. **鍵交換**: 以降の通信で使う**共通鍵（セッション鍵）**を安全に共有する
5. 以降のデータは**共通鍵暗号**で高速にやり取りする

> 💡 コツ: 「本人確認と鍵の受け渡しは公開鍵方式、本文のやり取りは高速な共通鍵方式」というハイブリッド構成です。

### サーバ証明書

サーバの**公開鍵**と**ドメイン名**を CA が署名で保証したものです。これにより「接続先が本物のサーバである」ことを確認できます（なりすまし防止）。

### SNI（Server Name Indication）

1台のサーバ（1つの IP アドレス）で複数の Web サイトを運用している場合、サーバはどの証明書を出せばよいか分かりません。そこで ClientHello に**接続したいホスト名**を入れて伝える拡張が SNI です。

🔴 ハンドシェイクの目的（相手確認+鍵共有）と SNI の役割は午後でも問われます。

### 確認問題

**問1.** TLS において、サーバ証明書を検証する主な目的はどれでしょう？

1. 通信速度を向上させるため
2. 接続先サーバが本物であることを確認し、なりすましを防ぐため
3. クライアントの身元をサーバに証明するため
4. パケットの到達順序を保証するため

<details><summary>答えと解説</summary>

正解: **2**

サーバ証明書は CA がサーバの公開鍵とドメイン名を保証したもので、クライアントはこれを検証して接続先の真正性を確認します。クライアント側の身元証明はクライアント証明書の役割です。速度向上や到達順序の保証は TLS の証明書検証とは関係ありません。

</details>

**問2.** TLS のハンドシェイク完了後、アプリケーションデータの暗号化に主に使われる方式はどれでしょう？

1. ハンドシェイクで共有したセッション鍵による共通鍵暗号
2. サーバの秘密鍵による公開鍵暗号
3. ハッシュ関数による一方向変換
4. 平文のまま送信し、受信側でのみ暗号化する方式

<details><summary>答えと解説</summary>

正解: **1**

TLS はハンドシェイクで安全に共有したセッション鍵を使い、以降のデータを高速な共通鍵暗号で保護するハイブリッド方式です。公開鍵暗号は処理が重いため鍵交換や認証に限定して使います。ハッシュは一方向変換なので復号が必要なデータ暗号化には使えず、平文送信では盗聴を防げません。

</details>

**問3.** SNI（Server Name Indication）の説明として、適切なものはどれでしょう？

1. サーバがクライアントの IP アドレスを確認する仕組み
2. 証明書の失効情報を CA に問い合わせる仕組み
3. DNS サーバにホスト名の正引きを依頼する仕組み
4. ClientHello で接続先ホスト名を伝え、1つの IP で複数サイトを運用するサーバが適切な証明書を選べるようにする拡張

<details><summary>答えと解説</summary>

正解: **4**

SNI は TLS ハンドシェイクの最初（ClientHello）で接続したいホスト名を伝える拡張で、同一 IP アドレスで複数のサイトをホストするサーバが正しい証明書を提示できるようになります。失効確認は OCSP や CRL、名前解決は DNS の役割であり、クライアントの IP 確認とも関係ありません。

</details>

**問4.** HTTP の通信を HTTPS に変更することで防げるようになる脅威はどれでしょう？

1. サーバへの大量アクセスによる DoS 攻撃
2. サーバ内のプログラムの脆弱性を突く攻撃
3. 経路上での通信内容の盗聴や改ざん
4. 利用者が推測されやすいパスワードを設定すること

<details><summary>答えと解説</summary>

正解: **3**

HTTPS(TLS) は通信経路を暗号化し、改ざん検知も行うため、経路上の盗聴・改ざんを防げます。DoS 攻撃は暗号化しても大量のリクエスト自体は届くので防げません。サーバ内部の脆弱性や利用者の弱いパスワードは通信の暗号化とは別の問題で、WAF や運用ルールなど他の対策が必要です。

</details>

## 3. メールのしくみ（SMTP・POP/IMAP・SPF/DKIM/DMARC）

メールは「送る」と「受け取る」でプロトコルが分かれています。郵便に例えると、ポスト投函から相手の郵便局までが **SMTP**、郵便受けから手紙を取り出すのが **POP3/IMAP** です。

### 送信と受信のプロトコル

| プロトコル | 役割 | ポイント |
|---|---|---|
| SMTP | 送信・サーバ間転送 | サーバ間は 25 番、利用者の送信（サブミッション）は 587 番+認証 |
| POP3 | 受信 | メールを**端末にダウンロード**して読む |
| IMAP | 受信 | メールを**サーバに置いたまま**読む。複数端末で同期しやすい |

### 送信ドメイン認証（なりすまし対策）

迷惑メールの多くは送信者（From）を偽ります。そこで「このドメインから送られたメールは本物か」を受信側が検証する仕組みが使われます。

- **SPF**: 送信元ドメインの DNS に「正規の送信サーバの IP アドレス一覧」を公開。受信側は実際の送信元 IP と照合する
- **DKIM**: 送信サーバがメールに**デジタル署名**を付け、受信側は DNS で公開された公開鍵で検証する（改ざん検知もできる）
- **DMARC**: SPF/DKIM の検証に**失敗したメールをどう扱うか**（受け取る・隔離・拒否）のポリシーをドメイン側が宣言する

> 💡 コツ: SPF=「送信元 IP で確認」、DKIM=「署名で確認」、DMARC=「失敗時の扱いを決める」と1行ずつで覚えましょう。

🔴 3つの役割の違いは午前Ⅱ・午後とも頻出です。

### 確認問題

**問1.** POP3 と比較したときの IMAP の特徴として、適切なものはどれでしょう？

1. メールの送信専用のプロトコルである
2. メールをサーバに置いたまま管理でき、複数の端末から同じメールボックスを参照しやすい
3. メールを必ず端末にダウンロードし、サーバからは削除する
4. DNS を使わずにメールサーバを探せる

<details><summary>答えと解説</summary>

正解: **2**

IMAP はメールをサーバ側に保持したまま読み書きするため、PC とスマートフォンなど複数端末での利用に向いています。端末へのダウンロードを基本とするのは POP3 の典型的な使い方です。送信は SMTP の役割で、宛先サーバの特定に DNS(MX レコード) を使う点はどの方式でも変わりません。

</details>

**問2.** SPF による送信ドメイン認証の仕組みとして、適切なものはどれでしょう？

1. メール本文を暗号化し、盗聴を防ぐ
2. 受信者がメールを開いたことを送信者に通知する
3. メールにデジタル署名を付与し、受信側が公開鍵で検証する
4. 送信元ドメインの DNS に公開された正規サーバの IP アドレス一覧と、実際の送信元 IP を照合する

<details><summary>答えと解説</summary>

正解: **4**

SPF は、ドメイン管理者が DNS に正規の送信サーバの IP アドレスを公開し、受信側が実際の送信元 IP と照合して詐称を検知する仕組みです。デジタル署名を使うのは DKIM です。本文の暗号化や開封通知は SPF の機能ではありません。

</details>

**問3.** DMARC の役割として、適切なものはどれでしょう？

1. SPF や DKIM の認証に失敗したメールの取り扱い（隔離・拒否など）のポリシーをドメイン側が宣言する
2. メールサーバ間の通信を TLS で暗号化する
3. メールボックスの容量を制限する
4. 添付ファイルのウイルススキャンを行う

<details><summary>答えと解説</summary>

正解: **1**

DMARC は SPF/DKIM の検証結果を踏まえ、認証に失敗したメールを「そのまま受け取る・隔離する・拒否する」のどれにするかをドメイン所有者が DNS で宣言する仕組みで、レポート送付の仕組みも持ちます。サーバ間の暗号化は SMTP over TLS、ウイルススキャンや容量制限はメールサーバ側の別機能です。

</details>

**問4.** 利用者がメールソフトから自社のメールサーバへメールを送信（サブミッション）する際の、一般的なポート番号と認証の組み合わせはどれでしょう？

1. 110 番ポートで認証なし
2. 443 番ポートで証明書のみ
3. 587 番ポートで SMTP 認証を行う
4. 53 番ポートで DNS 認証を行う

<details><summary>答えと解説</summary>

正解: **3**

利用者からの送信には587番ポート（サブミッションポート）と SMTP 認証を組み合わせるのが一般的で、迷惑メールの不正中継対策になります。110 番は POP3、443 番は HTTPS、53 番は DNS のポートであり、いずれもメール送信のサブミッション用途ではありません。

</details>

## 4. プロキシと CDN（フォワード/リバースプロキシ・キャッシュ）

**プロキシ（proxy）**は「代理」という意味で、クライアントとサーバの間に入って通信を中継する装置です。誰の代理をするかで2種類に分かれます。

### フォワードプロキシ（クライアントの代理）

社内の PC がインターネットへアクセスするとき、いったんプロキシサーバを経由させる構成です。

- **URL フィルタリング**: 業務に関係ないサイトや危険なサイトへのアクセスを遮断できる
- **キャッシュ**: 一度取得したコンテンツを保存し、2回目以降を高速化・回線節約
- **アクセスログの一元管理**: 誰がどこへアクセスしたか記録できる
- 外部からは**プロキシの IP しか見えない**ため、内部の PC を隠せる

### リバースプロキシ（サーバの代理）

Web サーバの手前に置き、外部からのリクエストをまず受け取る構成です。

- **負荷分散**: 複数の Web サーバへリクエストを振り分ける
- **TLS 終端**: 暗号化処理を肩代わりし、Web サーバの負荷を下げる
- **キャッシュ**: 静的コンテンツを代わりに返し、サーバの負荷を下げる

### CDN（Contents Delivery Network）

世界中・全国に配置された**キャッシュサーバ（エッジサーバ）**の網です。利用者は物理的に近いエッジからコンテンツを受け取るため、表示が速くなり、**オリジンサーバ（大もと）の負荷も下がります**。動画配信や大規模サイトで広く使われます。

🟡 「フォワード=クライアント側」「リバース=サーバ側」の向きをまず確実にしましょう。

### 確認問題

**問1.** フォワードプロキシを社内に導入する目的として、最も適切なものはどれでしょう？

1. 外部から社内 Web サーバへのアクセスを負荷分散する
2. 社内からインターネットへのアクセスを中継し、URL フィルタリングやログの一元管理を行う
3. 社内 LAN のIPアドレスを自動的に配布する
4. メールの送信ドメイン認証を行う

<details><summary>答えと解説</summary>

正解: **2**

フォワードプロキシはクライアント（社内 PC）の代理として外部アクセスを中継し、フィルタリング・キャッシュ・ログ管理を実現します。外部からのアクセスを受けて負荷分散するのはリバースプロキシの役割です。IP アドレスの自動配布は DHCP、送信ドメイン認証は SPF/DKIM などの仕組みです。

</details>

**問2.** リバースプロキシの説明として、適切なものはどれでしょう？

1. クライアントの Web ブラウザに組み込まれて動作するソフトウェアである
2. DNS の名前解決を高速化する専用サーバである
3. Web サーバの手前でリクエストを受け、負荷分散や TLS 終端、キャッシュ応答を行う
4. 社内 PC のインターネットアクセスを遮断する装置である

<details><summary>答えと解説</summary>

正解: **3**

リバースプロキシはサーバ側に置かれ、外部からのリクエストを最初に受けて複数サーバへの振り分けや TLS 処理の肩代わり、キャッシュ応答を行います。ブラウザ内のソフトウェアではなく独立したサーバや装置です。DNS の高速化はキャッシュ DNS サーバ、社内からのアクセス制御はフォワードプロキシや FW の役割です。

</details>

**問3.** CDN を利用することで得られる効果として、適切なものはどれでしょう？

1. 利用者に近いエッジサーバがキャッシュを返すため、応答が速くなりオリジンサーバの負荷も減る
2. 通信がすべて専用線経由になり、インターネットを使わなくなる
3. Web アプリケーションの脆弱性が自動的に修正される
4. DNS サーバが不要になる

<details><summary>答えと解説</summary>

正解: **1**

CDN は各地に分散配置されたエッジサーバにコンテンツをキャッシュし、利用者は近いサーバから受け取るため応答時間が短縮され、オリジンの負荷と回線使用量も減ります。通信はインターネット上で行われ、専用線化するわけではありません。脆弱性の修正は開発側の対応が必要で、CDN の利用にはむしろ DNS の仕組みを活用します。

</details>

**問4.** 「一度取得したコンテンツを保存しておき、同じ要求に対して保存したものを返す」仕組みを何と呼ぶでしょう？

1. ルーティング
2. カプセル化
3. フラグメンテーション
4. キャッシュ

<details><summary>答えと解説</summary>

正解: **4**

キャッシュは取得済みデータを一時保存して再利用する仕組みで、プロキシや CDN の高速化の核になります。ルーティングは経路選択、カプセル化は上位層のデータをヘッダで包む処理、フラグメンテーションはパケットの分割を指し、いずれも保存と再利用の仕組みではありません。

</details>
