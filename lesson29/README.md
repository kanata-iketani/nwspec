# 第29章 午後演習②：セキュリティ・クラウドの事例を読む

午後演習の後半は、午後Ⅱでも頻出のセキュリティとクラウドの事例です。DMZの再設計・リモートアクセスVPN・クラウド移行に伴うDNSとプロキシの見直しを、オリジナル事例で読み解きます。ここまで終えたら、仕上げは手持ちの過去問を時間を計って解いてください。

## 1. 事例演習: DMZ再設計と公開サーバのセキュリティ

セキュリティ系の事例では、🔴 「どのゾーンからどのゾーンへ、何を許可し、何を禁止するか」の表を頭の中に作りながら読むのがコツです。設問を先に確認してから本文へ進んでください。

---

**〔D社の公開サーバとDMZの再設計〕**

D社は、従業員300名の部品商社である。自社で公開Webサーバを運用しているが、過去の経緯から、①**公開Webサーバが社内のPCやファイルサーバと同じ内部LAN（192.168.1.0/24）に設置されている**。先日のセキュリティ診断で、この構成は危険であると指摘を受けた。

情報システム部のM部長と担当のNさんは、FW1を境界としてネットワークを外部（インターネット）、DMZ（192.168.100.0/24）、内部LANの3つのゾーンに分け、②**公開WebサーバをDMZに移設する**ことにした。移設後の主な設計は次のとおりである。

- Webサーバには固定グローバルIPアドレス203.0.113.10を割り当てる。FW1の静的NATにより、203.0.113.10宛ての通信はDMZの192.168.100.10（Webサーバ）に転送する
- FW1のルールは「許可する通信だけを列挙し、それ以外はすべて拒否する」方針とする

| 送信元ゾーン | 宛先ゾーン | 許可する通信 |
|---|---|---|
| 外部 | DMZ | 192.168.100.10宛てのTCP80と443のみ |
| DMZ | 内部 | Webサーバから内部のDBサーバ（192.168.1.20）宛ての特定ポートのみ |
| 内部 | DMZ | 管理用端末からの保守通信のみ |
| 外部 | 内部 | すべて拒否 |

Nさん: DMZ→内部をここまで絞る必要はあるのでしょうか。

M部長: ある。公開サーバは外部から直接アクセスされる以上、乗っ取られる前提で考える。③**Webサーバが侵害されても、そこを足掛かりに内部LANへ侵入を広げられないように**、DMZから内部へは業務に必要な最小限の通信だけを許可するのだ。

また、DNSについては、外部に公開する情報を持つ公開DNSサーバをDMZに、社内の名前解決を行う内部DNSサーバを内部LANに分離して設置する。

---

「移設の目的」「各ゾーン間で許可する通信」「DNS分離の狙い」の3点を整理してから設問に進みましょう。

### 確認問題

**問1.** 下線①の構成（公開Webサーバが内部LANに同居）が危険とされる理由として、最も適切なものはどれでしょう？

1. WebサーバのIPアドレスが足りなくなるため
2. 外部から攻撃を受けるWebサーバが侵害されると、同じLAN上のPCやファイルサーバへ直接攻撃が広がるため
3. 内部LANではHTTPが使用できないため
4. Webサーバの電源容量が不足するため

<details><summary>答えと解説</summary>

正解: **2**

公開サーバは外部からの攻撃に常にさらされています。内部LANに同居していると、サーバが乗っ取られた時点で攻撃者は社内PCやファイルサーバと同一セグメントに立つことになり、FWによる遮断が効きません。IPアドレスの枯渇、HTTPの可否、電源は本事例の論点ではありません。本番の記述なら「Webサーバ侵害時に、同一LAN上の内部機器へ直接攻撃が波及するため」（33字）と書きます。

</details>

**問2.** 下線②（WebサーバのDMZ移設）の目的として、最も適切なものはどれでしょう？（下線③のM部長の発言を踏まえること）

1. Webサーバの表示速度を上げるため
2. グローバルIPアドレスを節約するため
3. Webサーバが侵害されても、内部LANへの侵入拡大をFWで食い止められるようにするため
4. 内部LANのIPアドレス体系を変更するため

<details><summary>答えと解説</summary>

正解: **3**

M部長の発言のとおり、公開サーバは乗っ取られる前提で設計します。DMZに置けば、サーバと内部LANの間に必ずFW1が挟まり、DMZ→内部を最小限に絞ることで侵入の拡大（横展開）を防げます。表示速度やアドレス節約の効果はなく、内部LANのアドレス体系は移設と無関係です。本番の記述なら「Webサーバ侵害時も、内部LANへの侵入拡大をFWで防止できるようにするため」（37字）と書きます。

</details>

**問3.** FW1のルール表に基づき、外部（インターネット）からDMZ宛てに許可される通信はどれでしょう？

1. 192.168.100.10宛てのTCP80と443のみ
2. DMZ内のすべてのサーバ宛てのすべての通信
3. 192.168.1.20（DBサーバ）宛てのすべての通信
4. ICMPを含むすべてのプロトコル

<details><summary>答えと解説</summary>

正解: **1**

ルール表の1行目のとおり、外部→DMZはWebサーバ192.168.100.10宛てのTCP80（HTTP）と443（HTTPS）だけです。「許可する通信だけを列挙し、それ以外はすべて拒否」という方針なので、列挙されていない通信は全部落とされます。DBサーバは内部LANにあり、外部→内部はすべて拒否です。本番の記述なら「宛先をWebサーバ、ポートをTCP80と443に限定して許可する」（31字）のように対象とポートを明示します。

</details>

**問4.** DMZ→内部の通信を「DBサーバ宛ての特定ポートのみ」に絞る考え方の名称・趣旨として、最も適切なものはどれでしょう？

1. 冗長化（機器を2台にして可用性を上げる）
2. 最小権限の原則（業務に必要な通信だけを許可する）
3. 負荷分散（通信を複数サーバに振り分ける）
4. キャッシュ（同じ応答を使い回して高速化する）

<details><summary>答えと解説</summary>

正解: **2**

必要な通信だけを許可し、それ以外を拒否する考え方は最小権限の原則（最小限の許可）です。これにより、Webサーバが乗っ取られても攻撃者が内部へ届く経路はDBサーバの特定ポートだけに限定されます。冗長化は可用性、負荷分散は性能、キャッシュは高速化の技術で、アクセス制御の方針とは別の話です。本番の記述なら「業務に必要な最小限の通信だけを許可し、侵害時の影響範囲を限定するため」（35字）と書きます。

</details>

**問5.** 公開DNSサーバと内部DNSサーバを分離して設置する目的として、最も適切なものはどれでしょう？

1. DNSの応答速度を2倍にするため
2. ドメイン名を2つ取得するため
3. 内部のサーバ名やネットワーク構成の情報を、外部から引き出せないようにするため
4. 内部LANで名前解決を不要にするため

<details><summary>答えと解説</summary>

正解: **3**

1台のDNSサーバに公開情報と社内情報を同居させると、外部から社内のホスト名（サーバ名やその体系）を調べられるおそれがあります。外部に見せる情報は公開DNSに、社内の名前解決は内部DNSにと分離すれば、内部の構成情報が外部に漏れません。応答速度やドメイン数のためではなく、内部でも名前解決は引き続き必要です。本番の記述なら「内部のホスト名などの構成情報を外部から取得されないようにするため」（32字）と書きます。

</details>

## 2. 事例演習: リモートアクセスVPNの導入

テレワーク導入の事例です。🔴 VPNの問題では「経路（どこを通るか）」と「認証（誰を入れるか)」と「制御（入った後に何をさせるか）」の3点セットで整理すると設問に対応しやすくなります。

---

**〔E社のリモートアクセスVPN導入〕**

E社は、従業員200名のコンサルティング会社である。テレワーク制度の開始に伴い、従業員が自宅から社内の業務サーバを利用できるよう、リモートアクセスVPNを導入することにした。情報システム部のM課長と担当のNさんの検討内容は次のとおりである。

- DMZにTLS-VPN装置（VPN1、グローバルIPアドレス198.51.100.10）を設置する。①**TLS-VPNはTCP443を使用するため、自宅や外出先の多くのネットワーク環境からファイアウォールやNATを越えて接続しやすい**
- 利用者認証は、利用者ID・パスワードに加えて、会社が貸与するPCにインストールした②**クライアント証明書**を要求する
- VPN接続した端末には、VPN1がアドレスプール172.20.0.0/24からIPアドレスを払い出す
- FW1では、外部からVPN1宛てはTCP443のみ許可し、VPN1から内部へは、アドレスプール172.20.0.0/24を送信元とする業務サーバ宛ての必要な通信だけを許可する

Nさん: VPN接続中の端末がインターネットを利用するときの経路はどうしますか。社内宛てだけをVPNに流し、インターネット宛ては自宅回線から直接出す方式（スプリットトンネル）もありますが。

M課長: 当面は③**フルトンネル方式とし、端末のすべての通信をいったんVPN経由で社内に集め、社内のプロキシサーバとFW1を通して外部へ出す**。在宅勤務の端末であっても、通信の監視とURLフィルタリングを社内と同じ水準で適用したいからだ。

Nさん: その場合、VPN回線と社内設備に掛かる負荷は増えますね。利用者数の増加に備えて、帯域の監視をしておきます。

---

「TLS-VPNが選ばれる理由」「多要素認証の構成」「フルトンネルとスプリットトンネルの損得」を整理してから設問へ進みましょう。

### 確認問題

**問1.** 下線①のとおり、TLS-VPNが自宅などから接続しやすい理由として、最も適切なものはどれでしょう？

1. 暗号化を行わないので設定が不要だから
2. HTTPSと同じTCP443を使うため、多くの環境のファイアウォールやNATを越えやすいから
3. 専用線を自動で敷設してくれるから
4. 無線LANでしか使えない方式だから

<details><summary>答えと解説</summary>

正解: **2**

TCP443はHTTPSで常用されるポートで、家庭やホテルなどほとんどのネットワークで許可されています。そのためTLS-VPNは特別な穴あけなしに接続できる場面が多いのです。TLS-VPNはTLSで暗号化しますし、専用線を敷く技術でも無線限定の技術でもありません。本番の記述なら「HTTPSと同じTCP443を使うため、多くの環境でFWやNATを越えやすいから」（39字）と書きます。

</details>

**問2.** 下線②のとおり、ID・パスワードに加えてクライアント証明書を要求する目的として、最も適切なものはどれでしょう？

1. パスワードを覚えなくてよくするため
2. VPNの通信速度を上げるため
3. ID・パスワードが漏えいしても、証明書を持つ会社貸与PC以外からは接続できないようにするため
4. 証明書で通信ログを暗号化するため

<details><summary>答えと解説</summary>

正解: **3**

知識情報（ID・パスワード）に所持情報（クライアント証明書）を組み合わせた多要素認証です。パスワードがフィッシング等で漏れても、証明書が入った貸与PCがなければ接続できないため、不正アクセスを防げます。パスワード自体は引き続き使うので覚える負担はなくならず、速度向上やログ暗号化の機能でもありません。本番の記述なら「ID・パスワード漏えい時も、証明書を持つ貸与PC以外からの接続を防ぐため」（36字）と書きます。

</details>

**問3.** 下線③のフルトンネル方式を採用する目的として、最も適切なものはどれでしょう？

1. 在宅端末のインターネット通信にも、社内のプロキシによる監視とURLフィルタリングを適用するため
2. VPN回線と社内設備の負荷を減らすため
3. 自宅のルータを設定不要にするため
4. インターネットの利用を全面的に禁止するため

<details><summary>答えと解説</summary>

正解: **1**

M課長の発言のとおり、全通信を社内経由にすれば、在宅端末にもオフィスと同じ監視・フィルタリングを適用できます。これがフルトンネルの利点で、引き換えにVPN回線と社内設備の負荷は増えます（Nさんの指摘どおり、負荷軽減はスプリットトンネル側の利点）。自宅ルータの設定とは無関係で、プロキシ経由で外部へ出られるので利用禁止でもありません。本番の記述なら「在宅端末の全通信に社内と同水準の監視とフィルタリングを適用するため」（33字）と書きます。

</details>

**問4.** スプリットトンネル方式を採用した場合の留意点として、最も適切なものはどれでしょう？

1. 社内宛ての通信ができなくなる
2. インターネット宛ての通信が社内の監視やフィルタリングを経由しなくなる
3. VPN回線の負荷がフルトンネルより大きくなる
4. TCP443が使用できなくなる

<details><summary>答えと解説</summary>

正解: **2**

スプリットトンネルでは社内宛てだけがVPNを通り、インターネット宛ては自宅回線から直接出ます。負荷は軽くなる一方、その直接通信は社内のプロキシ・FWを経由しないため、監視やフィルタリングの統制が及ばなくなります。社内宛ての通信は従来どおりVPN経由で可能、負荷はむしろ減り、使用ポートは方式と無関係です。本番の記述なら「インターネット宛て通信が社内の監視・フィルタリングを経由しなくなる点」（34字）と書きます。

</details>

**問5.** FW1で、VPN1から内部への通信に対して行っているアクセス制御はどれでしょう？

1. VPN1からの通信はすべて無条件に許可している
2. アドレスプール172.20.0.0/24を送信元とする、業務サーバ宛ての必要な通信だけを許可している
3. 内部からVPN1への通信だけを許可している
4. TCP443以外の通信をすべて許可している

<details><summary>答えと解説</summary>

正解: **2**

本文の設計のとおり、VPN接続端末（送信元172.20.0.0/24）から業務サーバ宛てに必要な通信だけを許可しています。VPNで認証を通ったとしても、その先で何でもできてよいわけではなく、最小権限の原則はVPN利用者にも適用します。無条件許可は認証突破時や端末のマルウェア感染時に被害が広がり、残り2つは本文の設計と一致しません。本番の記述なら「VPN端末からは業務サーバ宛ての必要な通信のみを許可する」（28字）と書きます。

</details>

## 3. 事例演習: クラウド移行とDNS・プロキシの見直し

クラウド移行の事例です。🔴 この種の問題は「通信の集中がどこで起きるか」と「名前解決がどこで行われるか」を図に矢印で書き込みながら読むと、設問が一気に解きやすくなります。

---

**〔F社のクラウド移行とネットワークの見直し〕**

F社は、本社と4つの支店を持つ従業員500名の卸売業である。各支店は広域イーサネット網で本社と接続され、インターネット接続は本社に集約されている。社内PCのWeb通信は、すべて本社のプロキシサーバ（192.168.5.10）を経由して外部へ出る。社内の名前解決は本社の内部DNSサーバが行い、①**社内ドメインのゾーンは内部DNSサーバ自身が管理し、それ以外の外部ドメインの名前解決はフォワーダとして指定したISPのDNSサーバに転送している**。

このたびF社は、メールとファイル共有を外部のSaaSに移行した。移行後、②**本社のプロキシサーバと本社のインターネット回線の使用率が急上昇し、Web会議の音声が途切れる**などの影響が出た。情報システム部のM部長と担当のNさんが対策を検討した。

Nさん: 全支店のSaaS宛ての通信が、広域イーサネット網を通っていったん本社に集まり、プロキシと本社回線に集中していることが原因です。

M部長: では、③**信頼できる特定のSaaS宛ての通信に限り、プロキシを経由させず、各支店から直接インターネットへ出す**方式（ローカルブレイクアウト）を導入しよう。

Nさん: 対象の通信の振り分けは、PCのブラウザに配布するPACファイルで行います。宛先のドメイン名が対象SaaSのものであれば直接接続、それ以外は従来どおり本社プロキシを指定します。④**対象の判定はIPアドレスではなくドメイン名で行います**。SaaS事業者が接続先のドメイン名の一覧を公表しているので、それを基に設定します。

---

「帯域逼迫の原因」「ローカルブレイクアウトの目的」「なぜドメイン名で判定するのか」の3点を整理してから設問に進みましょう。

### 確認問題

**問1.** 下線②の問題（プロキシと本社回線の使用率急上昇）が起きた原因として、最も適切なものはどれでしょう？

1. SaaSのサーバが故障したため
2. 全支店のSaaS宛て通信が広域イーサネット網経由で本社に集まり、プロキシと本社回線に集中したため
3. 内部DNSサーバが停止したため
4. PCの台数が急に2倍になったため

<details><summary>答えと解説</summary>

正解: **2**

Nさんの分析のとおり、インターネット接続とプロキシが本社に集約された構成のまま、業務の中心がSaaSに移ったため、全拠点分のクラウド通信が本社の設備1点に集中しました。クラウド移行で通信量の構造が変わるのに経路が昔のまま、という典型的な問題です。SaaS故障やDNS停止なら「つながらない」症状になり、PC台数の記述は本文にありません。本番の記述なら「全拠点のSaaS宛て通信が本社のプロキシと回線に集中したため」（30字）と書きます。

</details>

**問2.** 下線③のローカルブレイクアウトを導入する目的として、最も適切なものはどれでしょう？

1. SaaSの利用料金を下げるため
2. 社内ドメインの名前解決を速くするため
3. 本社のプロキシ・インターネット回線・広域イーサネット網の負荷を減らし、SaaSへの通信の遅延を改善するため
4. 支店のPCからインターネットを利用できなくするため

<details><summary>答えと解説</summary>

正解: **3**

特定SaaS宛ての通信を各支店から直接出せば、本社までの広域イーサネット網、本社プロキシ、本社回線のすべてから該当トラフィックが消え、負荷と遅延の両方が改善します。利用料金や社内の名前解決の速度は変わらず、支店からのインターネット利用はむしろ直接可能になります。本番の記述なら「本社プロキシと回線への通信の集中を解消し、SaaS通信の遅延を改善するため」（37字）と書きます。

</details>

**問3.** 下線④のとおり、直接接続の対象をIPアドレスではなくドメイン名で判定する理由として、最も適切なものはどれでしょう？

1. SaaSの接続先IPアドレスは多数あり頻繁に変わるため、IPアドレスでの指定では管理しきれないから
2. ドメイン名のほうが通信速度が速いから
3. IPアドレスは暗号化されていて読めないから
4. PACファイルがIPアドレスを一切扱えないから

<details><summary>答えと解説</summary>

正解: **1**

**問4.** 下線①の構成で、社内PCが外部ドメイン（SaaSなど）の名前解決を行うときの流れとして、正しいものはどれでしょう？

1. PCがISPのDNSサーバに直接問い合わせる
2. PCが内部DNSサーバに問い合わせ、内部DNSサーバがフォワーダとして指定されたISPのDNSサーバに転送する
3. 名前解決は行われず、IPアドレスを手入力する
4. プロキシサーバがDNSのゾーンを管理している

<details><summary>答えと解説</summary>

正解: **2**

本文のとおり、PCの問い合わせ先は常に内部DNSサーバで、内部DNSサーバは自分が管理する社内ゾーン以外の名前（外部ドメイン）をISPのDNSサーバへ転送（フォワード）します。PCが外部DNSへ直接問い合わせる構成ではなく、名前解決なしの運用はあり得ず、ゾーン管理はプロキシではなくDNSサーバの役割です。本番の記述なら「内部DNSサーバが、外部ドメインの問合せをISPのDNSサーバへ転送する」（36字）と書きます。

</details>

**問5.** ローカルブレイクアウト導入後に残る留意点として、最も適切なものはどれでしょう？

1. 本社のプロキシサーバが不要になるので直ちに撤去すべきである
2. 直接接続にした対象SaaS宛ての通信は、本社プロキシの監視やログ取得を経由しなくなる
3. 広域イーサネット網が使用できなくなる
4. 社内ドメインの名前解決ができなくなる

<details><summary>答えと解説</summary>

正解: **2**

直接出す通信は本社プロキシを通らないため、その分の監視・URLフィルタリング・ログ取得が及ばなくなります。だからこそ対象を「信頼できる特定のSaaS」に限定しているのです。対象外の通信は引き続きプロキシ経由なので撤去はできず、広域イーサネット網は社内通信に使い続け、社内の名前解決は内部DNSサーバがそのまま担います。本番の記述なら「直接接続の通信はプロキシの監視とログ取得の対象外になる点」（29字）と書きます。

</details>
